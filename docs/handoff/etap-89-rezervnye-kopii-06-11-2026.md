# Этап 89 — внешние зашифрованные копии

Дата: 06.11.2026. Ветка: `etap-89-rezervnye-kopii`. Основа: `bff53bdd5c3a8413e260e47abc8af04d2cef91da`, main после принятого #104.

## Проблема и результат

Прежний обработчик сохранял открытый dump на локальном диске контейнера, не запускался стандартным Docker CMD, а проверка восстановления могла использовать тот же сервер и сравнивала число строк с текущей базой. Регулярное внешнее резервирование рабочего стенда не было подтверждено.

Добавлены S3, AES-256-GCM, обратное скачивание после загрузки, паспорт всех таблиц на общем снимке с pg_dump и восстановление на отдельном сервере с точной сверкой содержимого. Истории ежедневных, месячных и предмиграционных копий разделены. В образе клиент PostgreSQL 16, заранее собранный процесс расписания и проверка копии перед новыми миграциями. Владелец видит даты копии/восстановления и сбои в «Состоянии». Есть извлечение проверенного dump при недоступной исходной базе.

По умолчанию всё выключено. Реальные секреты, хранилище и рабочие данные в этом этапе не изменялись. Исторический перенос пяти записей weekly не входит в работу и не выполнялся.

## Решения

- Одна аутентифицированная единица хранения: зашифрованы и dump, и паспорт; неверный ключ/архив отклоняется до SQL.
- Пароль SQL не попадает в аргументы pg_dump/pg_restore. Ошибки внешних операций выводятся без сырых ответов с данными или секретами.
- Восстановление требует отдельного адреса/порта и явного подтверждения оператором. Создаётся уникальная новая база, удаляется только она; ошибка уборки не становится успехом.
- Локальная и внешняя копии имеют разные команды и отметки. Включённая переменная без свежего результата не означает защищённую базу.
- Один advisory lock предотвращает параллельное создание копий. Подготовка миграций сохраняет активный экспортёр снимка.
- Ежедневно 03:00 МСК, восстановление 1-го числа 04:00 МСК. 30 ежедневных файлов, 12 месяцев, 30 предмиграционных файлов; регулируется окружением.
- Команда ручного извлечения не восстанавливает поверх рабочей базы. Полный аварийный сценарий требует отдельного принятия владельцем и проверки восстановленных очередей.

## Проверки и найденные ошибки

Локально проверены шифрование/повреждение/неверный ключ, конфигурация, сохранение старых копий при сбое, ротация, отдельные базы и их уборка. Настоящие PostgreSQL 16 работают на портах 5547 и 5548 с вымышленными данными. SDK S3 проверен настоящими HTTP-потоками против локальной имитации, включая условную загрузку и все страницы списка; это не проверка конкретного внешнего провайдера.

Полный цикл обнаружил и помог исправить две ошибки: URI в PGDATABASE трактовался как буквальное имя базы (теперь --dbname без пароля); SQL LIKE `pg_%` исключал пользовательскую схему pgboss (теперь исключается только буквальный префикс `pg_`). Добавлена проверка восстановления очереди целиком и запуска собранного обработчика.

Первый общий прогон базы выявил различие локального часового пояса: роль работала в Europe/Moscow, а CI — UTC. Прямые SQL-вставки и Prisma давали разные времена в старом тесте экспорта. Исправлена только настройка локальной тестовой роли, продуктовый код и ожидания этого теста не менялись. Браузерные проверки выполнены с уже установленным Chromium через PW_CHROMIUM_PATH.

Локальные результаты перед PR и полный прогон GitHub фиксируются в описании PR. На компьютере нет Docker; сборка конечного образа и наличие клиентов проверяются в CI. В CI добавлен второй PostgreSQL и полный цикл резервирования внутри работы `baza`, а также запуск выключенного обработчика из готового образа.

## Что остаётся владельцу и ограничения

Перед слиянием — два независимых круга ревью и явное принятие. После отдельного запроса о ревью #105 владелец 07.11 поручил продолжать; первый круг завершён, второй проводится после исправлений. Слияние обновляет стенд, но внешнее резервирование останется выключенным до настройки.

Для первого включения нужны отдельный частный бакет/учётная запись, сохранённый вне приложения ключ шифрования и отдельный сервер восстановления. Совместимость конкретного S3, размер/время и потребление памяти на рабочей базе ещё не измерены. [Инструкция включения и аварийного восстановления](../rezervnye-kopii.md).

Код проверяет только адрес сервера, не физическую изоляцию за DNS. Один PUT ограничен 5 ГиБ. Проверка может создавать нагрузку на диск источника при сортировке таблиц; память ограничивается потоками, но сортировка PostgreSQL использует ресурсы базы. При аварийном SIGKILL временная база/файлы могут остаться: нужна ручная уборка после проверки назначения. Нет автоматической ротации ключей, восстановления глобальных ролей, резервирования Google-таблиц или point-in-time recovery.

Старые локальные `backup`/`backup:check` оставлены для совместимости; ими нельзя подтверждать внешний процесс. Политика хранения старых версий S3 при включённом versioning задаётся отдельно. До подтверждённой рабочей копии и пробного восстановления этап нельзя считать эксплуатационно завершённым.

## Первый независимый круг — 07.11

Ревьюер, не писавший код, нашёл три P2. Исправлено:

1. `npm run local/up` больше не запускает завершающийся при выключенных копиях процесс через `concurrently -k`, который останавливал вместе с ним сайт. Используется общий supervisor. Все браузерные тесты теперь запускают приложение через настоящую команду `npm run local`; 12 проверок состояния на двух ширинах прошли с выключенными копиями.
2. Старые очереди pg-boss получают новые настройки через `updateQueue`, поскольку `createQueue` не обновляет существующую запись. Интеграционный сценарий заранее создаёт обе очереди с прежними пределами, затем проверяет 3600 секунд и задержку повторов 300 секунд после запуска нового worker. Уже поставленные старые задания сохраняют свои собственные параметры до завершения.
3. CLI проверяет команду и число аргументов до доступа к базе/S3. `--help` только печатает справку; опечатки и лишние аргументы завершаются ошибкой использования. Создание копии возможно только без аргументов. Добавлены 11 модульных проверок, справка и три ошибки дополнительно проверены через собранный CLI с заведомо неверным адресом базы.

После исправлений прошли 1162 модульных теста, 9 интеграционных проверок копирования/восстановления, 12 браузерных проверок. Типы, линтер и сборка скриптов прошли. Основной код базы не менялся; исходные 1077 тестов и оба полных прогона GitHub #693/#694 прошли до исправлений. Новый полный прогон фиксируется в PR.

Ревьюер отдельно отметил, что потеря SQL-соединения после окончания снимка снимает advisory lock, но не прерывает уже начатые S3-операции. В первом круге утрата копии не была доказана; во втором найден воспроизводимый сценарий и исправлена публикация/ротация, см. ниже.

## Второй независимый круг — 07.11

Другой ревьюер проверил весь diff и исправления первого круга. Найдены два новых P2:

1. При потере SQL-lock пересекающаяся загрузка B могла попасть в ротацию A до проверки. При хранении одной копии A удалял свою подтверждённую копию, а B после ошибки скачивания удалял свой файл — история оказывалась пустой. Сценарий воспроизведён на двух операциях и барьерах в локальном хранилище с настоящим `pg_terminate_backend` только для случайной тестовой БД. После исправления ротация и автоматический выбор копии требуют пары архив + `.ready`; отметка создаётся после проверки архива. Неоднозначная ошибка PUT отметки не удаляет архив и не запускает ротацию. Одинокая отметка не считается копией; удаление пары начинается с отметки. Тест обрыва SQL теперь сохраняет и успешно восстанавливает A; дополнительно проверены оба исхода ошибки PUT отметки — до и после её фактического сохранения.
2. Query-параметр `dbname` мог перенаправить libpq в существующую базу, хотя pg создавал и проверял временную. Параметр `password` также оставался бы в аргументе команды. Общий валидатор адреса теперь вызывается при чтении конфигурации и непосредственно перед pg/libpq: разрешены только перечисленные TLS/Prisma параметры, overrides и повторения запрещены без вывода исходного URI. Проверены 11 запрещённых параметров, а интеграционный сценарий подтверждает отказ `dbname` до изменений на сервере восстановления.

Дополнительно нормализован порт по умолчанию (5432) у обоих клиентов. SQL-инструменты не наследуют PGHOSTADDR, PGSERVICE и прочие скрытые настройки адреса/сессии, а `--no-password` запрещает интерактивное ожидание пароля. Клиент pg использует фиксированные параметры сессии. Интеграционный цикл выполняется и при заведомо неверных PGHOSTADDR/PGSERVICE/PGPORT/PGOPTIONS в окружении.

После исправлений: типы и линтер прошли, 1174 модульных теста и 14 интеграционных проверок прошли. Второй ревьюер повторно проверил весь набор исправлений: оба P2 устранены, открытых подтверждённых P1/P2 нет; исправления первого круга сохранены. Самостоятельно полный прогон ревьюер не повторял. Новый полный прогон окончательной версии фиксируется в PR перед приёмкой. Старые архивы без `.ready` не участвуют в автоматической ротации; их можно явно проверить/извлечь. На рабочем стенде этот новый формат ещё не использовался.
