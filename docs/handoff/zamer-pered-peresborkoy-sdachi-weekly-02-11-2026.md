# Этап 87: замер живых данных перед пересборкой экрана «Сдать weekly»

Дата: 02.11.2026. Ветка `etap-87-zamer-pered-peresborkoy`, база — `main` на 98e6dd4a (этап 84, PR #94).
Основание: раздел «Что проверить на живых данных до начала пересборки» и решение 8 документа
`docs/resheniya-peresborka-sdachi-weekly.md` (ветка `resheniya-peresborka-sdachi`): миграция старых записей
необратима, до слияния владелец смотрит выборку за четыре недели и утверждает её.

Из среды разработки до живых данных не дотянуться: сети к стенду нет, мост к маку не подключён. Поэтому этап
не меняет приложение, а добавляет команду, которую владелец запускает сам на стенде и получает ответы.

## Как запустить

```
npm run measure:weekly
```

Адрес базы берётся из переменной окружения, как у `npm run backup` и `npm run reconcile:bord` (`DATABASE_URL`
или `DB_HOST` плюс `DB_PASSWORD`). Ни строки подключения, ни пароля в коде команды нет.

Необязательные ключи:

- `npm run measure:weekly -- --weeks 8` — сколько последних недель смотреть на привычку (по умолчанию 12,
  предел 52). Выборка миграции всегда за последние 4 недели: так сказано в решении 8.
- `npm run measure:weekly -- --out zamer.txt` — сложить тот же текст в файл рядом с командой. **Этот файл в
  репозиторий не коммитить:** в нём живые тексты записей, имена людей и названия команд.

Команда печатает всё в вывод, код выхода 0. Если база недоступна, пишет «Замер не сделан: ...» и выходит с 1.

## Что команда печатает

Пять ответов в один проход, человеческим текстом, без SQL и без счёта в голове.

1. **Записи и поля.** Сколько записей сдали за период, среднее за неделю (текущая отчётная неделя в среднее не
   идёт, она неполная), записи по неделям, и доля заполненных полей — «Влияние на бизнес», «Цифра или факт»,
   «Что делаем дальше», «Какая помощь нужна», ссылка — за весь период и отдельно по каждой из последних четырёх
   недель. Вывод по решению 14 печатается прямо, с порогом: ниже 15% — прятать «Влияние» и «Цифру» под
   «Добавить детали» дёшево; от 15% до 40% — решение обсудить заново; выше 40% — решение надо пересматривать.
   Порог взят из самого документа решений («одна запись из десяти» против «каждой второй»).
2. **Шаблоны блоков команд.** Сколько включённых команд (топ-команда не считается: по коду шаблона у неё нет),
   у скольких шаблон есть, сколько в них своих блоков и каких. Отдельно помечаются шаблон без блока «Продукты»
   и шаблон из одних блоков цифр: в них записи поедут не по смыслу. Если шаблонов нет ни у кого, так и
   написано: миграция и переезд ленты проще.
3. **Обрезка строки отчёта на 600 знаках** (`BLOCK_LIMITS.text`). Сколько записей в предел не влезает, какая
   доля, самая длинная строка, и три самых длинных примера: длина до и после и оба текста целиком. Это
   единственное место вывода, где печатаются полные тексты записей — они и есть предмет разговора.
4. **Люди в двух и более командах с разными шаблонами.** Кто это, его команды по порядку правила, чей шаблон он
   в итоге получает и какие блоки. Проверено по коду, а не на слух: правило `templateForAuthor` даёт не «шаблон
   первой команды», а шаблон первой команды из списка, **где шаблон задан**, причём в начале списка идут
   команды, которые ждут его weekly, и только за ними остальные его команды. Расхождения («первая команда без
   шаблона, правило взяло следующую») считаются отдельной строкой.
5. **Выборка миграции за четыре недели.** Блок считается по шаблону той команды, по которой человек сдаёт
   weekly (правило `templateForAuthor`); шаблона нет — по стандартному набору из восьми блоков решения 5, и это
   помечается. По правилу `entryBlockKey`: сколько записей в какой блок переезжает,
   «было и стало» по старому справочнику блоков, и почему именно туда (сдана по блоку шаблона, по смыслу, блока
   по смыслу нет — в «Продукты», ни того ни другого — в первый блок шаблона). Отдельным списком — случаи,
   которые решают, можно ли миграцию утверждать:
   - запись сдана по блоку, которого в шаблоне уже нет: блок записи теряется;
   - запись переезжает в блок, которого в шаблоне её команды нет (бывает, когда шаблона у команды нет совсем и
     блок считается по стандартному набору из восьми блоков решения 5);
   - запись переезжает в блок цифр, который ресурс собирает сам: строка записи там не сохранится;
   - у записи нет автора (общая запись «Все лидеры»): команды и шаблона у неё нет;
   - человек в нескольких командах, и в отчётах его команд одна и та же запись попадёт в разные блоки.

В пунктах 4 и 5 в выводе есть имена людей и названия команд: без них выборку не прочитать. Текстов записей там
нет, только начало фразы в 40 знаков, чтобы владелец узнал запись, блок и длину.

## Как сделано

- `src/lib/weekly-measure/survey.ts` — чистые функции: доли полей, шаблоны, обрезка, человек в нескольких
  командах, выборка миграции. Ни базы, ни ввода-вывода.
- `src/lib/weekly-measure/collect.ts` — чтение живых данных: недели периода, записи, команды с шаблонами,
  авторы с их командами.
- `src/lib/weekly-measure/text.ts` — вывод текстом.
- `scripts/measure-weekly.ts` — тонкая обёртка в стиле `scripts/reconcile-bord.ts` и `scripts/backup.ts`:
  `dotenv/config`, `prisma` из `src/lib/db`, `prisma.$disconnect()` в `finally`.

Правило переезда и пределы не переписаны второй реализацией: `entryBlockKey`, `entryText` и `BLOCK_LIMITS`
импортируются из приложения, шаблон автора — `templateForAuthor`, порядок команд — `expectingTeams` и
`loadTeamNodes`. Иначе выборка соврала бы о том, что сделает настоящая миграция. Блок «по смыслу» для объяснения
причины переезда тоже считается настоящим правилом: `entryBlockKey` вызывается второй раз на полном наборе
стандартных блоков, где блок по смыслу есть всегда.

Файлы открытых этапов (`weekly-submit.tsx`, `weekly-feed.tsx`, `submit-weeks.tsx`, `weekly-delivery.tsx`,
`weekly/service.ts`, `weekly/rules.ts`, `weekly/weeks.ts`, `weekly/submit-weeks.ts`, `weekly-blocks/types.ts`,
`ceo/report.ts`, `weekly/submit/page.tsx`, `admin/reload.ts`, `audit.ts`, `journal.ts`) не менялись: они только
читаются и импортируются. Кроме новых файлов в ветке изменён один существующий — `package.json`, строка
`measure:weekly`.

## Только чтение: что проверено

- В коде команды (`src/lib/weekly-measure/*.ts`, `scripts/measure-weekly.ts`) нет ни `create`, ни `createMany`,
  ни `update`, ни `updateMany`, ни `upsert`, ни `delete`, ни `deleteMany`, ни `executeRaw`, ни `queryRaw`, ни
  `$transaction`. Проверено поиском по этим словам: ни одного совпадения.
- Всё, что команда вызывает из приложения, тоже только читает: `currentReportingKey` → `getSetting`
  (`setting.findUnique`), `loadTeamNodes` → `team.findMany`, `templateForAuthor` → `teamWeeklyTemplate.findMany`.
  Недели команда не создаёт: `ensureWeek` не вызывается, непрочитанной недели для неё просто нет.
- Тест на настоящей базе снимает счётчики девяти таблиц (записи, недели, команды, участники, шаблоны, отчёты
  команд, журнал, люди, настройки) до замера и после, сверяет их и отдельно сверяет `updatedAt` шаблона: замер
  не меняет ни строки.
- Временных таблиц команда не создаёт: всё считается запросами на чтение и в памяти.

  правило переезда по всем ветвям (блок шаблона, забытый блок, по смыслу, «Продукты», первый блок, блок цифр,
  шаблона нет), группировка выборки и вывод текстом.
- `tests/db/weekly-measure.test.ts` — то же на настоящей базе: две команды (первая по порядку без шаблона,
  вторая с шаблоном и своим блоком «Найм и команда»), человек в обеих, записи с блоком шаблона, с забытым
  блоком, риск партнёрки, запись руководителя без шаблона и запись прошлой недели. Ловит главный случай,
  из-за которого владелец может выборку не утвердить: **запись переезжает в блок, которого нет в шаблоне её
  команды** (`outside-template`), и показывает, что у человека в двух командах та же запись в их отчётах
  попадает в разные блоки (`split-teams`).

## Чего в этой ветке нет

- Прогона проверок на машине: DNS в облачной сессии не работает, `npm ci` не проходит, поэтому ни линтера, ни
  типов, ни тестов локально. Проверки шли только в GitHub Actions по этому PR.
- Живых цифр. Команда готова, но данные видит только владелец на стенде: ответов на пять вопросов в этом
  документе нет и выдумывать их нельзя.

## Что дальше

1. Владелец запускает `npm run measure:weekly` на стенде и читает пять ответов.
2. Если «Влияние» и «Цифра» заполняются чаще, чем в четырёх записях из десяти, решение 14 пересматривается до
   начала пересборки.
3. Выборка миграции утверждается или не утверждается по списку спорных случаев. Пока она не утверждена,
   необратимый шаг миграции не делается (решение 8).
4. После этого заводится ветвь самой пересборки («weekly за 5 минут: одна классификация блоков», номер выдать
   по свободным: смотреть `git ls-remote --heads origin`).
