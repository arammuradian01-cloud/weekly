# Внешние резервные копии Weekly

Реализация этапа 89. По умолчанию выключена. Наличие этого кода не подтверждает, что рабочая база уже защищена: нужны настройки, первая внешняя копия и успешное восстановление. Старые команды `npm run backup` и `npm run backup:check` работают с локальными файлами и не заменяют этот процесс.

## Что подготовить

1. Частный S3-совместимый бакет по HTTPS и отдельный префикс, например `weekly-production`. Не использовать бакет служебных копий провайдера. Доступ: ListBucket только для своего префикса; GetObject, PutObject, DeleteObject только внутри него. Клиент не меняет ACL. Проверить запрет публичного доступа и поддержку условной загрузки `If-None-Match: *`.
2. Отдельный случайный ключ AES-256: 32 байта в каноническом base64. Хранить в секретах хостинга и независимом хранилище паролей владельца. Потеря ключа делает копии нечитаемыми. Нельзя менять ключ, пока нужны зашифрованные им старые архивы: автоматического набора исторических ключей пока нет.
3. Отдельный сервер PostgreSQL 16 для проверки восстановления. Роль должна иметь CREATEDB и доступ только к этому серверу. Не подключать туда приложение или фоновые обработчики. Имя или другой DNS-псевдоним рабочего сервера не делает его отдельным: код проверяет совпадение адреса и порта, фактическую изоляцию подтверждает оператор.
4. Достаточно диска на контейнере: одновременно могут находиться несколько размеров выгрузки (исходный dump, зашифрованный файл, контрольное скачивание; при восстановлении — архив, промежуточные открытые данные и dump). Одна загрузка ограничена 5 ГиБ. При недостатке места операция завершается ошибкой.

## Переменные

Пример имён — в `.env.example`; реальные значения задаются в защищённых переменных хостинга. Ключи и пароли не передавать в чат, PR, команды с видимыми аргументами или журналы.

| Переменная | Значение |
| --- | --- |
| `BACKUP_ENABLED` | `true` запускает расписание и защиту миграций; по умолчанию `false` |
| `BACKUP_S3_ENDPOINT` | HTTPS origin без пути и параметров |
| `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`, `BACKUP_S3_PREFIX` | Регион, частный бакет, собственный префикс |
| `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` | Отдельная учётная запись с ограниченными правами |
| `BACKUP_ENCRYPTION_KEY` | 32 случайных байта в base64 |
| `BACKUP_KEEP_DAILY`, `BACKUP_KEEP_MONTHLY`, `BACKUP_KEEP_MIGRATION` | По умолчанию 30 ежедневных файлов, 12 месяцев, 30 предмиграционных файлов |
| `BACKUP_RESTORE_ENABLED` | `true` для ежемесячной проверки; выключение не выключает ежедневные копии |
| `BACKUP_RESTORE_DATABASE_URL` | Адрес служебной БД отдельного сервера; каждая проверка создаёт новую временную БД |
| `BACKUP_RESTORE_ISOLATED` | `true` после подтверждения изоляции сервера оператором |
| `BACKUP_RESTORE_SSL_ROOT_CERT` | Путь к доверенному корневому сертификату сервера восстановления |
| `DB_SSL_ROOT_CERT` | Уже существующая настройка сертификата исходной базы |

При TLS рекомендуется проверка сертификата сервера: `sslmode=verify-full` и соответствующий корневой сертификат. Адрес исходной базы берётся из стандартных настроек Weekly. Для SQL-клиентов пароль передаётся через окружение дочернего процесса, не через аргументы.

## Первое включение

1. Принять и выложить код. Оставить `BACKUP_ENABLED=false`, пока хранилище и отдельный сервер не готовы.
2. Настроить перечисленные значения. Не менять права или содержимое рабочей базы ради проверки.
3. В терминале контейнера с настроенными секретами запустить `node dist/start/scripts/backup-remote.mjs`. Команда явно создаёт внешнюю ежедневную копию даже при выключенном расписании, скачивает её обратно и сверяет зашифрованные байты. Сразу проверить лимиты памяти, диска, длительность и ответ приложения под обычной нагрузкой.
4. Запустить `node dist/start/scripts/backup-remote.mjs verify`. Проверка должна создать, восстановить и удалить временную БД на отдельном сервере; ошибка удаления тоже означает неуспех. Проверить отсутствие оставшихся `weekly_restore_check_*` баз. При принудительном завершении контейнера `finally` не гарантирован: оставшуюся БД удаляет оператор после сверки её назначения.
5. Открыть владельцем «Состояние»: там должны появиться время копии и время проверенного восстановления. Эти отметки не содержат адресов или ключей.
6. Включить `BACKUP_ENABLED=true`, `BACKUP_RESTORE_ENABLED=true` и перезапустить контейнер. Проверить лог запуска расписания и следующую ежедневную отметку. При ошибке фонового процесса контейнер завершится, чтобы платформа увидела отказ. Ошибки заданий остаются в журнале и в списке сбоев, а при уже настроенных оповещениях — отправляются владельцу.
7. Подтвердить фактическое время и расход ресурсов на рабочем размере. Сервер сейчас небольшой; куча отдельного процесса копий ограничена 192 МБ, но это не предел суммарной памяти контейнера, SQL-клиентов и параллельной выкладки. При нехватке ресурса увеличить тариф или вынести обработчик в отдельный сервис перед постоянным включением.

Расписание: каждый день 03:00 МСК; проверка восстановления — 1-го числа 04:00 МСК. Пропущенное расписание pg-boss догоняет один раз. У заданий две повторные попытки с задержкой 5 минут. На странице состояния копия старше 36 часов и проверка старше 35 дней требуют внимания. Более поздний сбой также снимает успешную отметку состояния, сохраняя историю дат.

## Что проверяется и что хранится

`pg_dump --snapshot` и контрольные суммы таблиц используют один снимок PostgreSQL. Хешируется полное содержимое всех пользовательских таблиц во всех схемах, включая историю миграций и очередь pg-boss, с фиксированным представлением дат и сортировкой. После восстановления сравниваются набор таблиц, число строк и SHA-256 содержимого. Сравнение идёт с паспортом снимка, а не с уже изменившейся рабочей базой.

Архив `.wbk` содержит dump и паспорт внутри AES-256-GCM. Проверяются аутентификация архива и SHA-256 dump до вызова pg_restore. Внешний файл подтверждается обратным скачиванием и сверкой. Уникальные имена не перезаписываются. Временные файлы находятся в закрытой папке, открытые файлы восстановления — с правами 0600.

В префиксе три независимые истории: `daily/`, `monthly/YYYY-MM/`, `migration/`. Месячная копия — первая успешная ежедневная за московский месяц. Старые файлы удаляются только после подтверждения новой копии и только по формату имён Weekly. Частые выкладки не вытесняют ежедневную историю. Если S3 versioning включён, DeleteObject не удаляет предыдущие версии: отдельную политику их хранения задаёт владелец бакета.

Это логические копии конкретной базы. Роли PostgreSQL, глобальные настройки сервера, секреты, S3 и внешние Google-таблицы в архив не входят. Проверка данных таблиц не доказывает сохранность внешних файлов и всех серверных настроек; рабочие сценарии после аварийного восстановления проверяются отдельно.

## Перед изменением схемы

При `BACKUP_ENABLED=true` контейнер после подготовки базы проверяет новые миграции. Для непустой базы перед ними нужна подтверждённая внешняя копия в `migration/`; ошибка блокирует продолжение запуска. Пустая первоначальная база и запуск без новых миграций лишнюю копию не создают. Это защита стандартного запуска контейнера; ручной `prisma migrate deploy` вне этого запуска её обходит.

Если уже идёт ежедневная копия, предмиграционная попытка не работает параллельно и завершается ошибкой; повтор запуска выполняет платформа/оператор после завершения первой. Подготовка миграций не убивает специально помеченную сессию экспортёра снимка.

## Аварийное восстановление

1. Остановить запись пользователей и фоновые обработчики. Сохранить имеющуюся базу для диагностики; не удалять её.
2. Выбрать нужный ключ объекта из своего префикса. На доверенном компьютере или контейнере со свободным защищённым диском и нужным ключом выполнить `node dist/start/scripts/backup-remote.mjs extract '<ключ объекта>' '<путь к новому dump>'`. Исходная база для извлечения может быть недоступна; имя базы в настройках должно совпадать с именем в паспорте. Команда проверяет архив, не подключается к исходной базе и не перезаписывает существующий файл.
3. Восстановить dump клиентом PostgreSQL 16 в новую пустую БД на выбранном сервере: `pg_restore --no-owner --no-privileges --exit-on-error --single-transaction --dbname='<адрес без пароля>' '<dump>'`. Пароль передать безопасным окружением или pgpass. Не использовать `--clean` на существующей рабочей базе.
4. До запуска фоновых обработчиков проверить восстановленные очереди: старые задания могут повториться. Проверить вход, weekly, задачи, права, историю и соответствие схемы версии приложения; сверить результат с последним успешным пробным восстановлением и ожидаемой датой снимка.
5. Только после приёмки переключить приложение на восстановленную базу, затем включить фоновые процессы. После проверки удалить открытый dump. Старую базу сохранять до отдельного решения владельца.
