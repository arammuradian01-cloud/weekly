# Weekly Сравни

С этапа 57 ресурс для всей компании: weekly, задачи и просьбы команд Сравни. Первым прогноз и цифры ведёт департамент страхования и инвестиций.

Закрытый веб-ресурс: команда раз в неделю пишет итоги и ведёт общий список задач. Google-таблица Insurance&Invest Bord становится зеркалом в одну сторону (этап 6: пока только копия таблицы). Полное ТЗ лежит в проекте Claude «Сравни.ру», там же хэндоффы этапов.

Сейчас готов этап 1: вход, выбор профиля, режим управления, журнал, фирменная оболочка с пустыми разделами, ночные копии базы. Ресурс можно поднять тремя способами: в Timeweb Cloud с автообновлением из GitHub (основной), в GitHub Codespaces (посмотреть самому) и на своём Mac.

## Что внутри

- Next.js 16 и TypeScript, Tailwind CSS 4, цвета Сравни в одном месте: `src/app/globals.css`
- PostgreSQL 16 и Prisma 7, схема в `prisma/schema.prisma`, стартовые люди и справочники в `prisma/seed-data.ts`
- Фоновый процесс на pg-boss: копия базы каждую ночь в 03:00 по Москве и проверка восстановления 1-го числа
- Тесты: Vitest для правил (`tests/unit`), Playwright для входа на ноутбуке и телефоне (`tests/e2e`)

## Хостинг в Timeweb Cloud (основной способ)

App Platform собирает образ по `Dockerfile` из этого репозитория и выкатывает новую версию после каждого изменения выбранной ветки. База живёт отдельно, в управляемом PostgreSQL: тома в контейнерах платформы не сохраняются.

1. Зарегистрируйтесь на timeweb.cloud и пополните баланс.
2. Создайте базу: «Базы данных», PostgreSQL 16, минимальная конфигурация. В карточке базы на вкладке «Подключение» есть домен, пользователь и имя базы, на вкладке «Пользователи» кнопка «Скопировать» у пароля.
3. Создайте приложение: App Platform, тип Dockerfile, подключите GitHub через встроенную авторизацию (только так работает автодеплой), выберите репозиторий `weekly` и ветку `main` (до приёмки этапа можно `etap-1`). Конфигурация: не меньше 1 ГБ памяти.
4. Задайте переменные приложения. Все, кроме пароля, не секретны:
   - `DB_HOST`: домен базы с вкладки «Подключение», вида `xxxx.twc1.net`
   - `DB_PORT`: `5432`, `DB_USER` и `DB_NAME`: пользователь и база из карточки
   - `DB_SSL_ROOT_CERT`: `/app/certs/timeweb-managed-ca.crt`. Это корневой сертификат Timeweb из репозитория: с ним приложение проверяет, что говорит именно с вашей базой
   - `DB_PASSWORD`: пароль базы, вставляется как есть, кодировать спецсимволы не нужно. Его вставляет владелец аккаунта сам
   - `APP_URL`: адрес приложения из панели или свой домен (раздел «Свой адрес приложения» ниже), начинается с https://
   - `TRUST_PROXY`: `true`, `BACKUP_ENABLED`: `false` (уже заданы в образе, можно не трогать)
   - `GOOGLE_SERVICE_ACCOUNT_JSON`: ключ служебного аккаунта Google для выгрузки в таблицу, весь файл JSON как есть или в base64. Секрет: вставляет владелец аккаунта сам, в чат, документы, базу и репозиторий ключ не попадает. Без него ресурс работает, просто не пишет в таблицу
5. В расширенных настройках приложения укажите путь проверки состояния `/api/live` (он не зависит от базы). Запустите деплой. При старте контейнер сам применит миграции и стартовые данные.
6. Откройте журнал деплоя: пока пароли не заданы, при каждом запуске там появляется строка «Код первичной настройки». Откройте адрес приложения, нажмите «Перейти к первичной настройке», введите код и три пароля. После этого код гаснет.
7. Проверьте журнал в режиме управления: в колонке «Адрес» должен стоять ваш внешний адрес. Если там внутренний адрес вида 10.x или 172.x, значит перед приложением больше одного прокси: задайте `TRUST_PROXY_HOPS` = 2.

Ключ подписи сессий в облаке отдельно задавать не нужно: приложение выводит его из пароля базы. Если задать `SESSION_SECRET`, будет использоваться он. Вместо частей `DB_*` можно задать одну строку `DATABASE_URL`, она важнее. Вместо кода из журнала можно задать `SETUP_TOKEN` (не короче 16 символов).

Копии базы в облаке делает сам управляемый PostgreSQL, свои ночные копии там выключены.

## Свой адрес приложения (этап 69)

Технический адрес приложения в Timeweb (вида `имя-аккаунта-weekly-xxxx.twc1.net`) содержит имя аккаунта GitHub, и поменять его нельзя. Вместо него к приложению привязывается свой адрес. Технический адрес продолжает работать рядом. Адрес и переменные настраивает владелец аккаунта Timeweb, приложение к новому адресу готово: в коде адрес нигде не записан, он берётся из `APP_URL`.

### Основной вариант: бесплатное имя DuckDNS

1. В Timeweb: App Platform, приложение, вкладка «Настройки», блок «Домены», «Редактировать», вариант «Внешний домен». Впишите новое имя вида `<имя>.duckdns.org` и посмотрите в подсказке панели IP-адрес для A-записи. Сохранять удобнее после шага 2: сертификат выпускается, когда имя уже указывает на этот IP.
2. На duckdns.org заведите новое отдельное имя (бесплатно до пяти имён на аккаунт) и укажите у него этот IP вручную: поле с адресом у имени, затем «update ip».
3. В Timeweb сохраните домен. Привязка запускает повторный деплой. Дождитесь сертификата: Let's Encrypt выпускается и продлевается сам, новый адрес должен открываться по https без предупреждений браузера.
4. В переменных приложения поменяйте `APP_URL` на `https://<имя>.duckdns.org` без косой черты в конце. Добавьте `APP_ALIASES` = `https://<технический адрес>`: тогда, пока переход не включён, загрузки файлов (пакет рынка, борд лидера) работают и со старого адреса. В `APP_ALIASES` только точные адреса через запятую: шаблоны со звёздочкой (`*.twc1.net` открыл бы ресурс всем приложениям хостинга) и адреса не http и не https приложение отбрасывает. Сохраните, приложение перезапустится.
5. Откройте новый адрес и войдите по логину и паролю. Проверьте режим управления, «Настройки» и «Ссылку для входа» у любого человека: ссылка должна начинаться с нового адреса. Затем включите переход со старого адреса (раздел ниже).

Важно про DuckDNS:

- Для приложения нужно новое имя. Уже существующее личное имя с поддоменами не трогайте: оно указывает на ваш сервер, а все поддомены имени DuckDNS (`что-угодно.<имя>.duckdns.org`) всегда идут на тот же IP, что и само имя. Если поменять IP у прежнего имени или сделать приложение его поддоменом, перестанут открываться ваши другие страницы.
- Не добавляйте новое имя в скрипт автообновления IP на своём сервере или роутере: скрипт поставит у имени адрес сервера, и приложение перестанет открываться. IP приложения задаётся вручную один раз. Если Timeweb однажды покажет в подсказке другой IP, поменяйте его на duckdns.org так же вручную.
- Токен DuckDNS секретный, как пароль: в чат, документы и репозиторий он не попадает. Приложению он не нужен.

### Второй вариант: свой купленный домен

1. Возьмите домен или поддомен, например `weekly.<ваш домен>`. Поддомен домена из панели Timeweb сначала создаётся у самого домена.
2. App Platform, приложение, вкладка «Настройки», блок «Домены», «Редактировать». Выберите домен из списка панели или «Внешний домен» и впишите имя, затем «Сохранить». Привязка запускает повторный деплой.
3. Если домен у другого регистратора, добавьте у него A-запись на адрес из подсказки панели и дождитесь обновления DNS.
4. Дождитесь сертификата: Let's Encrypt выпускается и продлевается сам. Новый адрес должен открываться по https без предупреждений браузера.
5. В переменных приложения поменяйте `APP_URL` на `https://<новый адрес>` без косой черты в конце и добавьте `APP_ALIASES` = `https://<технический адрес>`, как в основном варианте.
6. Откройте новый адрес и войдите по логину и паролю. Проверьте режим управления, «Настройки» и «Ссылку для входа» у любого человека: ссылка должна начинаться с нового адреса. Затем включите переход со старого адреса (раздел ниже).

### Переход со старого адреса

Когда вход на новом адресе проверен, задайте в переменных приложения `REDIRECT_TO_APP_URL` = `1`. Страницы, открытые по техническому адресу, сами уходят на тот же путь и с теми же параметрами на новом адресе (переход 308). Браузер этот переход не запоминает: если убрать переменную, старый адрес снова открывается сам по себе сразу. Проверьте: откройте технический адрес, браузер должен оказаться на новом. Если браузер пишет «слишком много перенаправлений», удалите переменную и напишите разработчику: значит, хостинг передаёт приложению не тот адрес запроса.

Переход не трогает `/api`: проверка состояния `/api/live` и `/api/health` и лента календаря сроков работают по любому адресу, путь проверки состояния менять не нужно. Загрузки файлов и серверные действия (это POST) доделываются там, где начаты. Без `REDIRECT_TO_APP_URL` всё работает как раньше.

### Что меняется для людей

Входы. cookie входа привязана к адресу, поэтому на новом адресе каждый один раз входит заново: логин и пароль те же, режим управления включается заново. Старый вход на техническом адресе живёт до своего срока, после включения перехода им никто не пользуется; в профиле на вкладке «Вход и пароль» его можно завершить.

Старые ссылки. Ссылки для входа и подтверждения почты в уже отправленных письмах, ссылки в Google-таблице и в событиях календаря работают, пока жив технический адрес, а он живёт вместе с приложением. После включения перехода такая ссылка открывает тот же экран на новом адресе. Новые письма, приглашения, уведомления и строки таблицы сразу идут с адресом из `APP_URL`. Подписка на календарь сроков по старой ссылке продолжает работать, новую ссылку можно взять в профиле.

Приложение на экране «Домой» и уведомления в браузере привязаны к адресу: установите приложение заново с нового адреса и снова включите уведомления в профиле. Чтобы уведомления не приходили дважды, завершите в профиле старый вход этого устройства.

## Посмотреть без установки: GitHub Codespaces

1. На странице репозитория: Code, вкладка Codespaces, Create codespace на нужной ветке.
2. Подождите несколько минут: окружение само поставит PostgreSQL 16, зависимости и соберёт приложение.
3. В терминале codespace задайте пароли (`npm run password -- team`, `owner`, `admin`) и запустите `npm start`.
4. Во вкладке Ports откройте порт 3000. Ссылка по умолчанию открывается только вашим аккаунтом GitHub.

Это рабочее место разработчика, а не хостинг: оно засыпает примерно через 30 минут без действий, бесплатно 60 часов в месяц. Реальные данные туда не кладём.

## Первый запуск на Mac

Нужны Node.js 22 или новее и PostgreSQL 16 из Homebrew.

```
brew install postgresql@16
brew services start postgresql@16
/opt/homebrew/opt/postgresql@16/bin/createdb weekly

git clone https://github.com/arammuradian01-cloud/weekly.git ~/weekly
cd ~/weekly
npm install
npm run setup
```

`npm run setup` создаёт файл `.env` с новым ключом сессий, накатывает миграции и стартовые данные. Секреты в репозиторий не попадают.

Потом задайте три пароля. Каждый вводится в терминале и на экране не показывается, в базе хранится только хэш:

```
npm run password -- team     общий вход для команды, логин team
npm run password -- owner    режим управления владельца
npm run password -- admin    режим управления администраторов
```

Пароли должны быть не короче 12 символов и отличаться друг от друга. После смены общего пароля все выходят из ресурса.

## Резервные копии

- `npm run backup` делает копию сейчас. Копии лежат в папке `backups`: 30 ежедневных и 12 ежемесячных, старые удаляются сами.
- `npm run backup:check` восстанавливает последнюю копию во временную базу, сверяет таблицы с рабочей базой и удаляет временную.
- Фоновый процесс (`npm run local` или `npm run worker`) делает копию в 03:00 по Москве. Если компьютер спал, копия сделается один раз при следующем запуске.

Пока копии лежат на этом же компьютере. На сервере их нужно будет выносить во внешнее хранилище (раздел 6 ТЗ).

## Задачи и weekly из Insurance&Invest Bord

С этапа 7 выгрузка Bord загружается только по команде, сама при запуске она больше не подтягивается: иначе пустая база после сбоя тихо заполнилась бы старыми данными. Загрузить задачи и weekly из выгрузки: команды ниже или `BORD_IMPORT=on` для одного запуска сида. В репозитории лежат 51 задача из вкладки «Задачи» (`data/bord/zadachi-2026-10-05.csv`) и 51 запись weekly из вкладки «Weekly CEO» (`data/bord/weekly-ceo-2026-10-05.csv`, недели 38 и 39, встречи 22 и 29 сентября). Перед пилотом база заливается из свежей выгрузки: владелец в «Настройках», раздел «Перезаливка из выгрузки» (виден, пока плашка «Тестовый стенд»), или командой `reload:bord` ниже. Через настройки файлы не попадают в репозиторий.

```
npm run import:bord -- [файл]          загрузить задачи из CSV вкладки или выгрузки всей таблицы; существующие номера не трогаются
npm run import:bord-weekly -- [файл]   загрузить weekly из CSV вкладки «Weekly CEO»; работает только в пустую weekly
npm run reconcile:bord -- [файл]       сверить задачи ресурса с таблицей по каждому полю, код выхода 1 при расхождениях
npm run reload:bord -- --tasks <CSV> --weekly <CSV> [--yes]
                                       перезалить задачи и weekly из свежей выгрузки: без --yes только проверка,
                                       с --yes удаляет текущие задачи и weekly и загружает выгрузку (перед пилотом, с согласия владельца)
```

Как переносится weekly: каждая строка становится записью недели, которую разбирали на встрече из столбца «Дата встречи»; такие недели сразу закрыты. Автор по ФИО, «Все лидеры» становится общей записью без автора. Тип записи по блоку: «Риски и решения» дают риск, «Цифры и прогноз» результат, остальное событие. «Да» в столбце отчёта ставит отметку «В отчёт CEO». Ссылка из комментария уходит в ссылки записи, остальной текст комментария дописывается в «Подробнее». У каждого автора weekly этих недель считается сданным.

Как переносятся поля: «Перенесена» становится «В работе» с одним переносом без исходного срока; приоритет и состояние «не заданы»; «где сейчас» берётся из комментария, дата обновления из последней пометки «ДД.ММ:» в нём; направление по ответственному. Длинное тире заменяется дефисом.

## Настройки, журнал и выгрузка

- Люди, справочники и ритм недели правятся на экране «Настройки», без разработчика. Экраны берут их из базы.
- Справочники и ритм недели меняют владелец и администраторы в режиме управления, людей и роли только владелец.
- Скрытое значение справочника пропадает из выбора, но остаётся в старых записях. Типы записей можно переименовать и скрыть, новых не добавляют: на них держатся разделы отчёта CEO.
- Выключенный человек пропадает из выбора себя и из списков, его задачи и записи остаются. Последнего владельца выключить нельзя.
- Новый срок сдачи и день встречи действуют для недель, срок которых ещё не прошёл.
- Журнал пишет каждую правку: кто, когда, поле, было и стало. Правки черновика weekly до сдачи не пишутся, после сдачи пишется каждая. Фильтры журнала живут в адресе страницы.
- Владелец выгружает всё в Excel одним файлом (кнопка в «Настройках»): задачи, переносы, комментарии, weekly, недели, отчёты CEO, люди, справочники, журнал. Выгрузка тоже попадает в журнал.

## Забор задач из рабочего Bord

Решение Арама 06.10.2026: Insurance&Invest Bord остаётся главным, пока не готова финальная версия ресурса. Ресурс сам забирает из него задачи всех сотрудников и ничего в Bord не пишет.

С этапа 61 (решение Арама 21.10.2026) главное приложение, Excel-борд больше не ведём. Забор по расписанию по умолчанию выключен, даже если ссылка на Bord сохранена: его включает настройка `bord.pullOn`. Владелец включает забор на странице «Синхронизация» кнопкой «Включить забор» или вставив ссылку на Bord, останавливает кнопкой «Остановить забор по расписанию» (ссылка остаётся) или «Выключить забор» (ссылка стирается). «Забрать сейчас» работает и при выключенном расписании. Тесты, которым нужен забор по расписанию, включают его явно.

- Ресурс читает вкладку «Задачи» (колонки A:I, строки с номером под шапкой «№, Встреча, Ответственный…») раз в 5 минут, после ошибки через 15 минут. Цикл тот же, что у зеркала (`src/lib/sheet/runner.ts`), код забора в `src/lib/bord/`.
- Служебному аккаунту на Bord нужно только право «Читатель». Клиент Google для Bord получает токен только на чтение (`spreadsheets.readonly`), и любой запрос на запись падает до обращения к Google. Писать в рабочий Bord зеркало отказывается по-прежнему, на двух уровнях.
- Новая строка с номером становится задачей (метка `bord-pull`). Поле задачи меняется в ресурсе, только если оно изменилось в Bord с прошлого забора: правка, сделанная в ресурсе, живёт, пока это поле не поменяют в Bord. Прошлые значения полей хранятся в настройке `bord.snapshot`. При первом заборе прошлых значений нет, и всё, что расходится с Bord, берётся из Bord.
- Срок из Bord пишется переносом с причиной «Срок изменён в Bord», исходный срок не меняется. Закрытие в Bord ставит итог «Закрыта в Bord».
- Ответственный находится по ФИО в любом порядке, по фамилии с инициалом, по одной фамилии или имени, если такой человек один. Двое через запятую: первый ответственный, второй соисполнитель. Незнакомое ФИО ресурс добавляет в команду с ролью «Лидер» и направлением «Департамент» и показывает на странице «Синхронизация». Имя, которое подходит нескольким людям («Евгений»), новым человеком не становится: ответственный не меняется, проблема видна.
- Задачи, заведённые в ресурсе, получают номера от 1001: номера ниже у задач из Bord. Задача ресурса с номером ниже 1001 при заборе получает новый номер, это в журнале.
- Строка без номера, с повтором номера, без срока или с незнакомым статусом в ресурс не переносится или переносится частично и видна в списке проблем, пока её не поправят в Bord. Поменявшийся формат вкладки (колонки переставили, шапки нет) останавливает забор целиком, в ресурсе ничего не меняется.
- Задачу, которую удалили из Bord, ресурс не трогает и показывает в списке «Есть в ресурсе, нет в Bord».
- Номер, который в Bord отдали новой задаче (у строки другая дата встречи и другое название), не переписывает прежнюю задачу: она получает номер ресурса от 1001 со всей историей и попадает в список «нет в Bord», под старым номером создаётся новая задача.
- Статус «Поставлена» из Bord переносится как «В работе».
- Каждое изменение в журнале: источник «таблица», действия «Задача перенесена из Bord», «Задача изменена в Bord», «Номер задачи изменён».
- Страница «Синхронизация», раздел «Задачи из Bord» (владелец): ссылка на Bord, адрес служебного аккаунта, последний забор, что перенесено, новые люди, проблемы, кнопка «Забрать сейчас», история заборов. Выключить забор: «Выключить забор», задачи в ресурсе остаются.
- В имитации (`SHEET_FAKE=1`) забор читает выгрузку `data/bord/zadachi-2026-10-05.csv`.

## Зеркало в Google-таблицу для просмотра

Ресурс пишет все свои задачи (из Bord и заведённые в ресурсе), комментарии и weekly в отдельную таблицу для просмотра «Weekly: все задачи ресурса». Таблицу пишет только ресурс, правки в таблице ничего не меняют в ресурсе. У задач из Bord в колонке «Источник» пометка «(Bord)».

- Любая правка задачи, комментария, переноса, ссылки, соисполнителя или записи weekly попадает в очередь триггером базы в той же транзакции. Фоновый цикл в процессе сервера (`src/instrumentation.ts`) раз в 30 секунд отправляет очередь: правка видна в таблице меньше чем через минуту.
- Строки находятся по скрытой колонке «ID ресурса», значения пишутся как есть (RAW): текст, начинающийся с «=», не станет формулой. Даты пишутся числами с форматом даты.
- Вкладки ресурса: «Задачи» (без архива, просроченные красные), «Комментарии к задачам», «Weekly», «Журнал выгрузки», «Сводка» (формулы по лидерам). Отчёт CEO не выгружается. Вкладки защищены: кроме служебного аккаунта их может менять только владелец таблицы. Вкладки с такими же именами, которые были в таблице раньше, переименовываются в «… (архив до запуска)», остальные не трогаются.
- Если Google недоступен, правки ждут в очереди и уходят, когда он вернётся. Повторы через 1, 2, 4 минуты, дальше раз в 5 минут. Очередь старше 30 минут: предупреждение в шапке для режима управления.
- Ночью после 03:30 по Москве сверка сравнивает вкладки с базой: ручную правку возвращает и пишет в журнал (тип «Синхронизация»), лишние строки убирает, пропавшие дописывает.
- Страница «Синхронизация» (владелец), раздел «Таблица для просмотра»: ссылка на таблицу, адрес служебного аккаунта, очередь, последняя выгрузка и сверка, ошибки, кнопки «Выгрузить сейчас», «Сверить сейчас», «Пересобрать вкладки».
- В рабочий Insurance&Invest Bord зеркало не пишет: его ссылку страница не примет, а клиент Google для записи в него не создаётся.
- Без Google проверить можно в режиме имитации: `SHEET_FAKE=1` (так работают e2e-тесты). Выключить цикл совсем: `SHEET_SYNC=off`.

Как подключить таблицу для просмотра: создать в Google Cloud проект, включить Google Sheets API, создать служебный аккаунт и ключ JSON; положить ключ в переменную `GOOGLE_SERVICE_ACCOUNT_JSON` на Timeweb; создать пустую Google-таблицу и дать адресу служебного аккаунта доступ редактора; вставить ссылку на неё на странице «Синхронизация».

## Таблица-связка с LRF и цифрами недели

Прогноз месяца и цифры недели ресурс читает не из боевых файлов, а из отдельной таблицы «LRF для Weekly». В ней по вкладке на каждый нужный лист источника, в A1 формула IMPORTRANGE на занятую область этого листа с запасом. Доступ служебному аккаунту даётся только к этой таблице: к боевым LRF, к таблице метрик и к недельному отчёту «Weekly Sravni» у ресурса доступа нет. Руками в связке ничего не правят.

- Источники: LRF «INSURANCE & INVEST» (вкладки без префикса), LRF партнёрского канала (префикс «B2B. »), недельный отчёт «Weekly Sravni», из него только лист TOTAL (префикс «Weekly. »). Оттуда ресурс и читает. Таблица метрик (префикс «Metrics. ») связана для людей: ресурс её не читает, но вкладки занимают место в пределе ячеек. Листы ERE (затраты на персонал) и метрики других департаментов не берутся.
- Вкладки ставит скрипт `scripts/sheets/svyazka-lrf.gs`: его код вставляют в редактор скриптов самой связки («Расширения», «Apps Script») и запускают руками. `linkAll` связывает новые листы, `svyazkaPereschet` пересчитывает размеры уже связанных, `svyazkaProverit` показывает вкладки с ошибкой в A1, `svyazkaRazbit` пересобирает слишком большие, `svyazkaPochinit` переписывает формулы заново, `svyazkaSbros` начинает очередь сначала.
- Три предела Google, из-за которых скрипт устроен сложнее, чем кажется: шесть минут на прогон (скрипт работает частями, запоминает место и продолжает со следующего запуска), 10 млн ячеек на таблицу (вкладка получает размер занятой области источника с запасом, листы связываются в порядке «сначала нужные ресурсу»), размер одного IMPORTRANGE (большие листы берутся частями по строкам и склеиваются в одну вкладку).
- Имена листов, которые читает ресурс, лежат и в коде (`src/lib/plan/spec.ts`, `src/lib/plan/partners.ts`), и в скрипте: внутри Google импортировать код ресурса нельзя. Расхождение ловит `tests/unit/svyazka-script.test.ts`.
- Запас на вкладке 200 строк и 40 столбцов. Когда источник вырастет сильнее, `linkAll` этого не заметит: уже связанные вкладки он пропускает не глядя. Раз в квартал и после больших правок в LRF стоит запустить `svyazkaPereschet`, он пройдёт по всем вкладкам и подгонит размер; прогон долгий, запускать до строки «Очередь пройдена».
- Разделитель аргументов в формулах зависит от локали таблицы: в русской это точка с запятой. Скрипт определяет его пробной формулой и запоминает, `svyazkaSbros` забывает.
- Первый раз каждую пару таблиц нужно связать вручную: открыть вкладку источника в связке и нажать «Открыть доступ» в подсказке у A1.
- Ссылку на связку вставляют на странице «Синхронизация»: как источник прогноза и как источник цифр недели с вкладкой «Weekly. TOTAL».

## Личные входы (этап 9)

Каждый входит под собой по одноразовой ссылке, журнал записывает настоящего автора и способ входа.

- Ссылку выдаёт владелец: «Настройки», «Люди и роли», «Ссылка для входа». Ссылка показывается один раз, живёт 3 дня и открывает вход один раз; в базе хранится только её отпечаток. Отправлять лично, не в общий чат.
- Если заданы `SMTP_URL` и `MAIL_FROM`, человек с почтой в списке людей получает ссылку сам на экране входа. Письменная ссылка живёт 15 минут. Ответ одинаковый, есть адрес в списке или нет; не больше 5 запросов с адреса и 3 писем человеку за 15 минут.
- Ссылка открывает экран с кнопкой «Войти»: почтовые сканеры и мессенджеры открывают ссылки сами, поэтому вход случается только по нажатию.
- Вход живёт 30 дней на устройстве. В «Профиле и входах» видно, где открыт вход, там же «Выйти на всех устройствах». Владелец завершает входы человека в списке людей, выключение человека завершает их само.
- Общий логин team работает переходный период. Выключает его владелец: «Настройки», «Вход», «Только личный». Выключить можно, только войдя самому по личной ссылке.
- Режим управления при личном входе включается паролем управления или, если почта настроена, ссылкой на почту.
- Владелец не может войти: `npm run login-link -- <короткое имя или почта>` в консоли сервера печатает ссылку на 3 дня.

«Нет на неделе»: в профиле человек отмечает отпуск или больничный на неделю с замещающим, владелец отмечает коллегу в списке людей, кнопка «Отсутствие». Weekly за эту неделю не ждём: человек виден серым в полосе сдачи и не входит в счёт «сдали N из M», на встрече видно, кто замещает, сданный всё же weekly не считается опозданием.

## Логины, рабочая почта и главный владелец (этап 52)

- У каждого логин: первая буква имени и фамилия латиницей (amuradyan), совпадение решается номером (amuradyan2). Входить можно по логину, по прежнему короткому имени и по подтверждённой почте. Логин меняет владелец в списке людей; team, all, system и admin заняты ресурсом.
- Пароль человек придумывает сам по личной ссылке, владелец паролей не видит. «Ссылки всем без пароля» выдают ссылки пачкой на 3, 7 или 14 дней и выгружают CSV (ФИО, должность, логин, ссылка). Файл даёт вход каждому из списка: не пересылать целиком и удалить после рассылки. Владельцам и администраторам ссылки только по одной.
- После первого пароля человек видит экран с логином и предложением указать рабочую почту. Адрес начинает работать после ссылки из письма (сутки, один раз). Смена почты просит текущий пароль, владельцы и администраторы меняют почту только в режиме управления, прежний адрес получает письмо о смене. Домены настройкой `auth.email.domains`, по умолчанию только sravni.ru, поддомены перечисляются отдельно.
- Главный владелец и совладельцы. У совладельца те же права, но главного меняет только он сам: роль, почту, логин, пароль, ссылку для входа, завершение входов, назначение другого главного. Главный записан в настройке `owner.primary`, при первом запуске её заполняет сид.
- Подпись роли владельца (этап 69). По умолчанию главный подписан «Владелец», остальные владельцы «Совладелец». Главный владелец при личном входе в режиме управления задаёт подпись себе и совладельцам: «Настройки», «Люди и роли», кнопка «Подпись роли» в строке владельца. Например себе «ex-Владелец», совладельцу «Владелец». От 2 до 30 знаков: буквы, цифры, пробел, дефис, точка, запятая и скобки; пустое поле возвращает подпись по умолчанию. Подпись видна в шапке и меню профиля, в профиле, на экране выбора себя, в сводке «Люди», в настройках и в выгрузке в Excel. Права подпись не меняет: их по-прежнему решают роль и главный владелец. Подписи лежат в настройке `owners.titles`, каждая правка в журнале с тем, что было и что стало; со снятием роли владельца подпись снимается.
- Логин закрывается после 5 неверных попыток с любых адресов на 15 минут: это защита от подбора. Закрытый человек входит по ссылке на почту.

## Структура всей компании (этап 53)

- Файл структуры с колонкой «Департамент» описывает всю компанию: корень «Сравни», руководитель компании генеральный директор (строка без департамента и подразделения с «Руководит» да). Департамент страхования и инвестиций, загруженный раньше, встаёт под компанию со всеми подразделениями, людьми и командами.
- Файл без колонки «Департамент» грузится только в департамент руководителя топ-команды: подразделения, вакансии и люди других департаментов не трогаются.
- Команды на трёх уровнях: команда генерального директора наверху, под ней топ-команда и команды руководителей департаментов, под ними команды руководителей управлений. Руководителей отделов и секторов в файле можно не ставить: тогда в команде руководителя управления все его люди.
- Руководитель собирает свою команду из людей любых веток: поиск по всей компании на экране «Weekly-команды» (с этапа 64, раньше «Структура», вкладка «Команды»). Человек не из ветки руководителя помечен «другая ветка»: он и его руководитель получают событие в «Мне», а его задачи вне этой команды руководителю не видны. Задачу такому участнику руководитель предлагает, а не ставит сразу.
- Файл для загрузки собирается из листа структуры без кадровых полей и в репозиторий не попадает.

## Согласование задач в другие департаменты (этап 54)

- Задача человеку из другого департамента: его руководитель согласует её или только узнаёт о ней. Где что действует, задаёт владелец: «Настройки», «Согласование задач», правило по умолчанию и отдельно для департаментов. По умолчанию информирование.
- Правило берётся по департаменту того, кому ставят задачу. Департамент человека: подразделение уровня «департамент» над ним или подразделение прямо под компанией. Руководитель по линии подчинения ставит своим людям без согласования, задача себе тоже.
- «Согласование»: задача приходит предложенной, принимает или не согласовывает её только руководитель ответственного (за него режим управления). «Информирование»: задача ставится как обычно, руководитель получает событие в «Мне» и видит задачу. Передача задачи человеку из другого департамента проходит то же правило.
- Правило считается от автора задачи: передача внутри чужого департамента не обходит его. Автор без места в структуре считается человеком из другого департамента. Просьба, которую адресат сделал задачей, проходит правило от автора просьбы.
- Передачу не согласовали: задача возвращается прежнему ответственному в тот же статус, серия, просьбы и связи не трогаются. Отклонённую задачу ответственный или руководитель команды открывают только через новое согласование; режим управления открывает сам.
- Режим управления не ждёт согласования: руководитель ответственного только узнаёт о задаче. Решение и событие согласования только при личном входе, общему логину они не видны.
- Соисполнитель из департамента с согласованием добавляется только режимом управления, иначе ему ставят отдельную задачу. Из департамента с информированием: его руководитель получает событие с номером и названием задачи.
- Автор задачи для правила хранится в задаче: тот, кто поставил, автор просьбы, из которой она сделана, или тот, кто передал задачу без автора (из Bord). Не согласованную задачу закрыть иначе («Выполнена») может только согласующий или режим управления. Отказ в передаче возвращает и «Все лидеры», и задачу без ответственного. Передача ждала решения, а нового ответственного выключили: задача возвращается прежнему.
- Согласующий: включённый руководитель ответственного, иначе руководитель подразделения выше. После загрузки структуры, смены руководителя или подразделения и выключения человека согласующие пересчитываются и у согласованных задач, пачками, прежнему событие закрывается, новому приходит. Смена настройки уже поставленные задачи не пересчитывает. Согласующий подписан на задачу, видит правки названия и результата, может комментировать. Повтор согласованной задачи остаётся согласованным.

## Цель задачи по тексту (этап 55)

- В форме новой задачи поле «Цель» заполняется само: слова названия и результата сравниваются со словами целей, которые задаче можно дать (своей команды и команд выше на квартал сегодня и квартал срока, личные цели ответственного). Номер цели в тексте («РТ-1») выбирает её сразу.
- Цель подставляется, только если она заметно лучше остальных. Человек может выбрать другую поиском по названию или коду или нажать «Без цели»; после ручного выбора подбор цель не меняет. Сменили команду или срок и выбранная цель больше не подходит: подбор начинается заново.
- В карточке задачи выбор цели тоже с поиском, подходящие по тексту цели вверху с пометкой «по тексту». Внешних сервисов подбор не использует, всё считается на сервере приложения.

## Задачи к целям перетаскиванием (этап 65)

Задача Арама 22.10: сотрудник перетаскивает к каждой цели задачи, которыми занимался или которые видел. Правки после двух кругов независимой проверки 22.10 описаны по месту.

- Страница «Цели», вкладка «Связать задачи с целями» (`/goals?mode=link`, квартал в адресе: `&q=2026-Q4`). Слева, на телефоне сверху, цели на квартал карточками: название с кодом, владелец, «закрыто 1 из 3», факт и целевое. Цифры цели одним правилом и одной подписью на обеих вкладках страницы (таблица, дерево, карточка): отменённые и только предложенные задачи не считаются, закрытыми считаются выполненные (`countsForGoal`, `goalTasksText` в `src/lib/goals/links.ts`). На карточке они считаются по задачам под кнопкой «Задачи», то есть по тем, что видны человеку; на вкладке «Цели квартала» к задачам цели добавляются задачи целей ниже. Группы: «Мои цели» (личные, в том числе из бордов лидеров), цели своих команд, «Команды ниже: «…»» (у руководителя: подчинённые команды по структуре, их цели и задачи) и «Цели выше» (команд выше, на которые работает команда). Чужую личную цель видит только руководитель её команды или команды выше. Снятые цели не показываются: к ним задачу не привязать.
- На ноутбуке колонка целей закреплена и прокручивается сама: задачу не тащат через всю страницу. До нижних целей задачу доносят двумя способами: колесом прямо во время перетаскивания (карточка задачи под курсором колесо не перехватывает) или подведя курсор к верхнему или нижнему краю колонки, тогда колонка крутится сама, тем быстрее, чем ближе к краю (`edgeStep`; край считается по видимой части колонки). Пока задачу тянут, после любой прокрутки места целей перемеряются, иначе перетаскивание промахнулось бы мимо закреплённой колонки.
- Справа «Мои задачи»: что человек ведёт или вёл (ответственный, соисполнитель, поставил задачу), задачи его команд и команд ниже, и что он видел: задачи, где он комментировал, где его упомянули в комментарии, и задачи, за которыми он следит. Отметки «открывал задачу» в базе нет, поэтому «видел» значит эти случаи. Всё только среди задач, которые человек видит по правилам сервиса задач. Сверху задачи, которые он может привязать: открытые по сроку, ниже закрытые за квартал, без отменённых и архива. Задачи, которые он только видит, лежат отдельно в свёрнутом блоке «Только посмотреть» с пояснением, кто может их привязать: лёгкими строками без перетаскивания, только когда блок открыт, по 30 с «Показать ещё». Строки и карточки запомнены и получают постоянные обработчики: поиск, отметка и начало перетаскивания перерисовывают только то, что поменялось. Свои задачи (ведёт, поставил, соисполнитель, комментировал, упомянут, следит) приходят все отдельным запросом; предел 500 открытых и 200 закрытых только у задач команд и команд ниже, и экран говорит, если он сработал. Фильтры «Без цели» (по умолчанию) и «Все» и их счётчики считают только доступные задачи, поиск по номеру и словам действует на оба списка.
- Задачу тянут на карточку цели: связь ставится, с другой цели перевязывается, в зону «Без цели» снимается. Отмеченные галочкой задачи тянутся вместе, для них же кнопки «Привязать к цели…» и «Снять цель». Тянутся и привязываются только отмеченные задачи, которые видны на экране: отмеченные, но скрытые поиском или фильтром, остаются на месте, и плашка выбора так и пишет. Отметка снимается только с задач, которые сдвинулись; не прошедшие возвращаются в выбор. Карточка цели раскрывается кнопкой «Задачи»: там все задачи цели, которые человек видит, их можно перетащить на другую цель или отвязать крестиком. Подсказки «Отпустите, чтобы привязать» и «Не подходит этой задаче» появляются поверх карточки: карточки не прыгают, когда задачу берут.
- Мышью перетаскивание начинается после сдвига, пальцем долгим нажатием, с клавиатуры: Tab до задачи, пробел берёт её, стрелки ведут по целям по порядку, пробел привязывает, Escape отменяет. Стрелки не двигают карточку задачи и не прокручивают страницу: цель подсвечивается по выбору стрелкой, колонка целей сама прокручивается к ней. Экранный диктор слышит по-русски, что взято и над какой целью. Без перетаскивания то же кнопкой «К цели» у задачи и выбором цели из списка, на телефоне это основной способ. Цели, которые задаче не подходят, во время перетаскивания приглушены и не принимают её, в списке выбора выключены с пояснением.
- Фокус не теряется: если привязанная задача ушла из списка «Без цели», фокус встаёт на следующую строку, иначе на предыдущую, иначе на заголовок «Мои задачи». То же после окна «К цели»; если строка осталась, фокус возвращается на её кнопку. После крестика в карточке цели фокус на следующем крестике или на кнопке «Задачи». После «Снять цель» и «Снять отметку» у отмеченных фокус на заголовке «Мои задачи».
- Правка видна сразу, тост «Задача 12 привязана к цели «D1. Маржа»» с кнопкой «Отменить» на 5 секунд. Если сервер отказал, задача возвращается на место. Если часть задач не прошла, тост ошибки говорит, что получилось и что нет: «Не получилось с задачей 15: …», «Задача 17 не подходит цели …», «Нет прав менять цель: задача 18». Цель, которую уже успел поставить кто-то другой, считается успехом, отменять там нечего.
- Права те же, что в карточке задачи, проверяет их сервис задач (`setTaskGoal` в `src/lib/tasks/service.ts`, правило `canChangeGoal` в `src/lib/goals/links.ts`): ответственный, соисполнитель (он тоже занимается задачей, решение после проверки 22.10), тот, кто поставил задачу, руководитель команды задачи или команды выше и режим управления. Наблюдатель цель не меняет. Общий логин без режима управления видит только топ-команду и меняет цель только у своих задач. Подходит цель своей команды или команды выше или личная цель ответственного и соисполнителей, текущего квартала или квартала срока, не снятая. Подсказки и отказы называют всех, кто может менять цель, включая руководителя команды выше и режим управления. Такие цели человек и так видит: цели видны всем.

Отмена возвращает прежнюю цель, только если задачу с тех пор не трогали; прежнюю цель успели удалить: отменить нельзя. Миграции нет, связь по-прежнему одно поле `Task.goalId`.
- Подбор цели по тексту (этап 55) только предлагает цель новой задаче в форме и в черновиках разбора встречи. Цель уже заведённой задачи он не меняет: связь, поставленная руками, живёт при правке названия, закрытии и новых подсказках. Это закрепляет `tests/db/goals-link.test.ts`.

## Weekly-команды (этап 64)

Решение Арама 22.10: управление командами было размазано по «Структуре» (вкладка «Команды») и «Weekly-проектам», теперь один экран «Люди», «Weekly-команды» (`/people/teams`). Новых правил нет: права, согласие руководителя (этапы 53 и 57) и журнал те же, экран лишь показывает только разрешённые кнопки.

- Список: все weekly-команды, которые человек видит. Владелец и администратор в режиме управления видят все команды компании; руководитель свои команды по структуре, свои проекты, команды ниже своих (пометка «команда ниже вашей»: им он задаёт, кто сдаёт weekly и срок, как раньше в «Структуре») и команды, где он участник; остальные команды, где они участники, только для просмотра; общий логин без режима управления только топ-команду и только для просмотра. По каждой команде: название, вид (по структуре или проект), руководитель, «в команде N человек» (вместе с руководителем, то же число в карточке), ждём ли weekly и срок, сколько сдали за отчётную неделю, сколько ждут согласия. Порядок: команды, где вы руководитель, потом команды ниже ваших, потом где вы участник, потом остальные. Поиск по названию, руководителю, участникам и ждущим (когда команд больше трёх).
- Владелец и администратор без режима управления видят только свои команды; экран говорит об этом в шапке и в карточке («Включите режим управления, чтобы видеть все команды и назначать руководителей») со ссылкой на включение; после включения режима страница возвращает в ту же карточку (`/manage?next=`). Своя топ-команда владельца без режима управления подписана «Состав топ-команды меняют в режиме управления», а не «только просмотр».
- «Создать команду»: название и сразу люди поиском по всей компании, можно нескольких (одна транзакция, `createProjectWith`). Руководит командой тот, кто создаёт. Владелец в режиме управления сразу выбирает другого руководителя в поле «Руководитель»: команда создаётся сразу с ним той же транзакцией (`createProjectWith` с `leader`), место в дереве (под командой руководителя по структуре), дубль названия, предел своих команд и очередь считаются по руководителю, люди добавляются по его ветке, события в «Мне» называют его. Выбрав другого руководителя, владелец может добавить участником себя. Остальным окно говорит, где назначают руководителя. Пустой список: понятное действие, «Создать команду» руководителю или ссылка на структуру остальным.
- Карточка команды: на ноутбуке панель справа, на телефоне отдельный экран с кнопкой «К списку команд». Карточка, открытая из списка, это шаг в истории (помнится и после обновления страницы): «К списку команд», закрытие команды и кнопка «Назад» браузера возвращают к списку одним шагом, без лишних записей. На телефоне фокус переходит на заголовок карточки и обратно на строку команды, на ноутбуке остаётся в списке. Без выбранной команды на телефоне в списке ничего не подсвечено, на ноутбуке показана и подсвечена первая команда, а адрес не меняется: выбор строки человеком ничем не перебивается. Выбранная команда в адресе (`?team=`): ссылкой на карточку можно поделиться, события «Мне» о составе команды ведут сюда, переход на вкладку «Weekly-команды» возвращает к списку. Поля нажатия на телефоне не меньше 44 точек. Команда, которой нет в вашем списке (например, вашего сотрудника позвали в чужую команду), открывается по ссылке только для просмотра.
- В карточке: участники списком с ролью, должностью и подразделением, пометка «другая ветка»; «Добавить участников» поиском по всем людям компании с множественным выбором (`addProjectPeople`: своя ветка сразу, другие ветки после согласия их руководителя, в режиме управления владельца сразу); «Убрать» (`removeTeamMember`); «Ждут согласия руководителя» с согласующим и «Отменить» (`cancelJoinRequest`: просивший, руководитель команды, владелец); «Переименовать» (свой проект руководитель через `renameProject`, любую команду владелец в режиме управления через `updateTeam`); «Назначить руководителя» и команда выше (владелец в режиме управления, `updateTeam`, кнопкой в шапке карточки); «Кто сдаёт и срок» (кнопкой в шапке карточки): weekly специалистов, срок сдачи и встреча (`setTeamRhythm`, руководитель команды, руководитель выше, владелец); «Закрыть команду» (свой проект руководитель через `closeProject`, ожидающие запросы отменяются; любую, кроме топ-команды, владелец через `updateTeam`, ожидающие запросы тоже отменяются той же транзакцией), только когда в команде нет открытых задач. Права в карточке, открытой по ссылке, считаются теми же правилами, что в списке.
- «Ваших сотрудников зовут в команды»: запросы, которые ждут вашего согласия, решаются на этом экране (прежние ссылки на «Структуру» ведут сюда). Владелец в режиме управления видит закрытые команды и может вернуть их, и кнопку «Создать команды по структуре».
- Перетаскивание подразделений и людей осталось помощником «Собрать из структуры» внутри экрана, свёрнутым по умолчанию; раскрытый помощник остаётся раскрытым до конца сеанса во вкладке браузера. Бросить можно в свои команды, в выбранную команду (владелец) и в «Новую команду».
- В «Структуре» команды только для просмотра со ссылкой «Управлять командами» и «Карточка команды»; загрузка структуры и правка людей и подразделений остались там. В переключателе команды в шапке последний пункт «Управлять командами»; у кого одна команда и переключателя нет, на его месте ссылка на этот экран. Серверные тексты сервиса проектов говорят «команда», а не «проект».

## Разбор встречи из Notion (этап 61)

Решение Арама 21.10.2026: Excel-таблица с бордом больше не главная, главное приложение. Итоги встречи, weekly для CEO и задачи собираются из заметки встречи в Notion и проверяются ведущим.

- На странице встречи команды (`/weekly/meeting`) кнопка «Разобрать встречу из Notion»: ведущий вставляет ссылку на страницу встречи (домены notion.so, notion.com, app.notion.com, *.notion.site). Встречи за неделю ещё нет: повестка собирается сама. Разбор открывается на странице `/meeting/notion/<id>`. Пока он идёт, экран пишет «Разбираем встречу…» и обновляется сам.
- Сроки: на чтение Notion всего 90 секунд, что не успели, отмечается «текст обрезан по времени», и разбор идёт по прочитанному. Ответ Claude ждём до 4 минут. Обрыв запроса, когда от общего срока оставалось меньше таймаута запроса, и ожидание после «слишком много запросов» тоже считаются нехваткой времени: текст обрезается, разбор не падает. Идущий разбор раз в 15 секунд обновляет отметку «жив»; без неё больше 75 секунд разбор считается зависшим (например, сервер перезапустился): в списке разборов встречи он «Завис», его можно повторить, а экран продолжает ждать и подхватит поздний результат. Новый разбор той же страницы закрывает зависший с пометкой «Прервано: запущен новый разбор этой страницы». Повтор, создание задач и отправка CEO не проходят одновременно: строка разбора блокируется, и проходит что-то одно.
- Ресурс читает страницу через Notion API: заголовок, все блоки с пагинацией и вложенные блоки до четвёртого уровня, вложенные страницы не открывает. Блоки, которые Notion API не отдаёт текстом (AI-заметки встречи, расшифровки, всё, что API помечает unsupported), считаются, и итоги пишут, сколько не прочитано. Страница без текста для разбора: «не разобрано» с объяснением.
- Текст с заголовками и списками разбирает Claude по API. Без ключа или если Claude не ответил, разбор идёт правилами: разделы «Итоги», «Решения», «Задачи», «Риски», «Что дальше», строки списков и чек-боксы, «Ответственный: Фамилия», «@Имя», «Фамилия: что сделать», сроки «до 25.10», «до пятницы», «до конца недели». Экран честно пишет, чем разобрано.
- Текст встречи уходит в Claude как данные: системная инструкция прямо говорит, что всё внутри заметки не команды. Ответ принимается только через инструмент по схеме и проверяется на сервере, лишние символы (длинное тире, стрелки) заменяются. Ничего не создаётся само: всё становится черновиком.
- Вкладки разбора: «Итоги» (главное, решения, риски, что дальше и, ведущим, текст страницы), «Weekly для CEO» (черновик по смысловым блокам отчёта CEO, с этапа 66, и предпросмотр собранного отчёта), «Задачи» (черновики задач и решения встречи по одному). Когда разбор готов или не получился, тот, кто запустил эту попытку (первый запуск или «Повторить»), и руководитель команды получают событие в «Мне». Предпросмотр собранного отчёта (цифры, решения и благодарности топ-команды) видят только те, кто отправляет CEO; остальные ведущие видят свои разделы черновика.
- «Отправить CEO» только в приложении: отчёт CEO за неделю встречи сохраняется и помечается отправленным (кто, когда, кому) со снимком разделов и «Моих встреч». CEO получает событие в «Мне» и видит на странице «Отчёт CEO» собранный отчёт только для чтения: цифры недели и итог прогноза месяца (по уровню доступа к цифрам этапа 57, у генерального все), разделы из снимка, решения недели, благодарности, «Мои встречи недели». Цифры, решения и благодарности собираются живыми за ту неделю. Если отчёт после отправки поправили в приложении, CEO видит пометку и отправленную версию. CEO: руководитель подразделения уровня «компания» в структуре, если его нет, включённый профиль CEO (короткое имя ceo). Отправляют владелец и администраторы в режиме управления при личном входе: отчёт CEO за неделю у департамента один. Смотрит CEO тоже при личном входе.
- Отчёт CEO за неделю уже есть: черновик его молча не затирает. Экран показывает, кто и когда сохранил отчёт, и предлагает «Дописать по разделам» (строки встречи в конец каждого раздела, строки, которые уже есть, второй раз не попадают) или «Заменить отчёт» (видно, что будет заменено). «Мои встречи недели» остаются. Если отчёт поменяли, пока ведущий смотрел разбор, отправка просит обновить страницу.
- Черновик задачи: название, что нужно сделать, ответственный из людей компании, соисполнители, срок, направление, команда встречи, цель, источник «Встреча». Цель в черновике та же, что получит задача: цель черновика, если она всё ещё подходит команде, людям задачи и кварталу срока, иначе подбор по тексту (этап 55) тем же правилом, что у создающего. Срок не назван: через неделю после встречи, с подсказкой проверить. Ответственного, которого ресурс не узнал однозначно, нужно выбрать или снять задачу: иначе задачи не создаются.
- «Создать задачи» ставит все отмеченные разом, одной транзакцией через сервис задач: задачи людям других департаментов уходят на согласование их руководителю или он узнаёт о них (этап 54). Ошибка в одной задаче откатывает все. Повторное нажатие, в том числе двойное, ничего не дублирует. Решения встречи записываются в журнал решений тем же нажатием, только отмеченные: по умолчанию все сняты, текст можно поправить.
- Повторный разбор той же страницы: если по этой встрече и странице задачи уже созданы, окно показывает их номера и спрашивает, разбирать ли ещё раз. В новом разборе черновики, похожие на созданные задачи (то же или почти то же название и тот же ответственный), сняты и помечены «уже есть задача N».
- Права: разбор видят те, кто видит встречу команды. Запускают, повторяют и правят ведущие: руководитель команды, руководитель выше, режим управления. Полный текст страницы видят только ведущие при личном входе, остальные участники видят итоги и черновики. Наблюдателю и общему логину черновик weekly для CEO не показывается. Создать задачи может ведущий при личном входе. Общий логин не отправляет CEO и не создаёт задачи.
- Журнал: запуск, чем и сколько разобрано, ошибки, правки черновика, отправка CEO, созданные задачи. Текст встречи в журнал и логи сервера не пишется.
- Прежний «Приём из Notion» этапа 23 (вставить текст разбора руками) остался на встрече кнопкой «Вставить текст».

Что поставить в переменных приложения в Timeweb:

- `NOTION_TOKEN`: ключ внутренней интеграции Notion (Internal Integration Secret). Секрет: вставляет владелец аккаунта сам, в чат, документы, базу и репозиторий ключ не попадает. Без него разбор пишет, что ключ не задан.
- `ANTHROPIC_API_KEY`: ключ Claude API. Секрет так же. Без него разбор идёт правилами.
- `ANTHROPIC_MODEL`: модель Claude, не секрет. По умолчанию `claude-sonnet-5-5`.
- `NOTION_ALLOWED_PARENTS`, необязательно: ID страниц или баз Notion через запятую (можно ссылками), из которых разрешено разбирать встречи. Если задана, страница встречи должна лежать под одной из них: ресурс поднимается по родителям страницы до пяти уровней (страница, база, блок). Иначе разбор отказывает: «Эта страница не лежит в разделах Notion, из которых ресурсу разрешено разбирать встречи». Родителя, не расшаренного на интеграцию (Notion отвечает 404 или 403), ресурс не видит, поэтому разрешённый раздел тоже нужно расшарить; таймаут, лимит запросов и сбой Notion при проверке остаются ошибкой Notion, повтор может пройти. Пока переменная задана, копии синхронизированных блоков с других страниц не читаются: их оригинал может лежать вне разрешённых разделов, итоги пишут, сколько таких блоков. Переменная задана, но ни одного ID в ней не разобрать: разбор закрыт с понятным текстом, в журнале сервера предупреждение без значения переменной. Не задана: можно разбирать любую страницу, расшаренную на интеграцию.

Как подключить Notion:

1. В Notion: «Настройки», «Подключения», «Разработать или управлять интеграциями» (страница notion.so/profile/integrations), «Новая интеграция». Тип «Внутренняя», рабочее пространство Сравни, возможности: только «Читать содержимое». Скопировать Internal Integration Secret в `NOTION_TOKEN` и перезапустить приложение.
2. Расшарить страницы встреч на интеграцию: на странице встречи меню с тремя точками справа вверху, «Подключения», найти интеграцию и подтвердить. Удобнее сделать это один раз на родительской странице со всеми встречами: доступ получат все вложенные страницы. Её же удобно указать в `NOTION_ALLOWED_PARENTS`.
3. Если страница не расшарена, разбор пишет «Notion не отдал страницу: её нет или она не расшарена на интеграцию» и предлагает повторить.

Тесты настоящие Notion и Claude не вызывают: транспорт подменяемый. `NOTION_FAKE_DIR` (фикстуры `tests/fixtures/notion/*.json`) и `ANTHROPIC_FAKE_DIR` (ответы `tests/fixtures/claude/<id страницы>.json`, у остальных страниц разбор правилами) только для тестов: в рабочем образе (NODE_ENV=production) они ничего не включают, кроме сквозных тестов с флагом `WEEKLY_E2E=1`, который ставит только `playwright.config.ts`. В Timeweb их не задают. `NOTION_API_BASE` и `ANTHROPIC_API_BASE` меняют адрес API, по умолчанию официальные адреса.

## Новости и дайджесты (этап 60)

Решение Арама 21.10: блок новостей по каждому продукту и ежедневный и еженедельный дайджест с источниками. Правки после независимой проверки 21.10 описаны ниже по месту.

- Источники: публичные ленты RSS и Atom (Банк России, союзы страховщиков, отраслевые и деловые СМИ). Список и ключевые слова по продуктам ведёт владелец в «Настройках», раздел «Новости». Стартовый список лежит в `src/lib/news/sources.ts` и добавляется сидом один раз в пустую таблицу; дальше сид его не трогает. Удаление источника с подтверждением, там же предлагается просто выключить ленту.
- Новость хранится как заголовок, дата, источник, ссылка, продукты и короткое описание в одну-две фразы, не длиннее 240 знаков. Без ключа Claude описание это начало анонса источника дословно, и так оно подписано в интерфейсе: «Начало анонса источника». С ключом это короткий пересказ, подпись «Пересказ Claude». Статьи целиком не копируются, статья открывается на сайте источника. Из описания вырезаются адреса, почта, телефоны, призывы перейти и служебные хвосты («Подробности на сайте», «Тел.:», «Источник:», «Фото:»); длинное тире, стрелки и точка-разделитель в анонсах, заголовках и ответе Claude заменяются дефисом.
- Разбор лент линейный: один проход по тегам, без DTD и внешних сущностей, не больше 1 МБ текста и 200 записей из ленты. Кодировка по метке BOM (UTF-8, UTF-16), объявлению XML или charset заголовка (в кавычках тоже); сжатие gzip, br, deflate с заголовком zlib и без него, цепочки вроде «gzip, gzip», предел 5 МБ и до, и после распаковки. Дата без часового пояса читается как UTC, дата позже чем через 5 минут от забора заменяется временем забора.
- Привязка к продуктам по ключевым словам: слово ловится по началу («страхов» находит «страхование» и «страховщик»), в словосочетании каждое слово по началу («тарифн коридор» находит «тарифного коридора»), слово в кавычках только целиком (`"Сравни"` находит «Сравни.ру», но не «сравнил»; `"ВЗР"` не находит «взрыв»). Новость без слова ни по одному продукту не сохраняется. Название самой ленты признаком не считается: на ленте Банки.ру слово «Банки.ру» не относит новость к партнёрке. У источника есть «строгая привязка» для общих деловых лент: к продукту нужно два разных слова этого продукта.
- Claude: если на сервере задан `ANTHROPIC_API_KEY`, привязка и описание уточняются отдельным проходом после забора (модель из `ANTHROPIC_MODEL`, по умолчанию claude-sonnet-5-5), пачками по 5 новостей. Модель может только сузить продукты, найденные словами: добавить продукт или обнулить список нельзя, если она убрала всё, остаются слова. Текст новостей уходит модели как данные, ссылки, почта и телефоны вырезаются до отправки и из ответа. В настройках «подключено» только после удачного вызова, последняя ошибка видна там же (без ключа). Без ключа всё работает по правилам.
- Где видно: раздел «Новости» с фильтром по продуктам в адресе (`/news?d=osago,kasko`, `/news?d=my` для своих продуктов, повтор параметра берёт первый) и блок «Новости» на главной «Моя неделя» по продуктам человека. Если продуктов нет (нет направления и ничего не выбрано в профиле), «Мои продукты» пустые с подсказкой выбрать продукты, а не вся лента. Страницы ленты сохраняют фильтр.
- Дайджест: ежедневный по будням и еженедельный в понедельник, окно 8:00-12:00 по Москве, один на человека и период. Ежедневный собирает новости с прошлого непустого дайджеста человека, но не дальше 7 дней (первый за 36 часов): в понедельник приходят и пятница, и выходные, после праздников ничего не теряется. Время новости это фактическое время её сохранения, нижняя граница берётся с запасом 15 минут, а новости, уже ушедшие человеку за 8 дней, не повторяются: новость, сохранённая в том же проходе, что и дайджест (или «Забрать сейчас» параллельно), попадает в следующий. Еженедельный, не собравшийся в понедельник (сервер лежал), уходит первым проходом позже на неделе, по будням с 8:00 до 20:00, но только если цикл новостей работал ещё до конца понедельничного окна (время первого прохода хранится в `news.loop.startedAt`) и у человека был еженедельный за прошлую неделю. При выкате во вторник вечером, новому сотруднику и тому, кто только включил рассылку, первый еженедельный приходит в ближайший понедельник. Приходит в «Мне» тихим событием (предмет `news:<id>`, в счётчик меню и в «ждут вашего внимания» не входит, открытие страницы дайджеста `/news?digest=<id>` отмечает его просмотренным) и письмом, если почта настроена. В письме новости по продуктам из подписки человека, у каждой источник, дата и ссылка. Пустой дайджест не отправляется; пустой ежедневный не записывается, пустой еженедельный записывается для защиты от повтора. Письмо, которое не ушло (почта лежала), повторяется следующими проходами в течение шести часов; строку письма процесс сначала захватывает, поэтому два контейнера не отправят одно письмо дважды. Если почта легла посреди прохода, дайджесты и события в «Мне» остальным записываются сразу без попыток письма, письма подбирает повтор.
- Частоту и продукты человек выбирает в профиле, вкладка «Письма и уведомления». По умолчанию (решение Арама 22.10: приложение теперь для всей компании) дайджест не приходит никому, пока человек сам не включит его в профиле; продукты по умолчанию его направления. У тех, кто уже выбрал частоту, она остаётся. «Департамент» и «Страхование в целом» раскрываются во все продукты страхования.
- Цикл новостей свой, со своей арендой в базе (`src/lib/news/loop.ts`), отдельно от цикла писем: долгий забор не задерживает напоминания и письма. Каждую минуту: дайджесты в своё окно, раз в час забор лент с общим сроком 90 секунд (источник не начинается, если до конца срока меньше 20 секунд; что не успели, заберём в следующий час, первыми идут дольше всех не забиравшиеся; обрыв по общему сроку не считается сбоем источника), уточнение через Claude не дольше 2 минут, раз в сутки очистка. Аренда продлевается между шагами. Ленты скачиваются до четырёх сайтов одновременно, ленты одного сайта друг за другом, а сохраняются строго по порядку списка источников: перепечатку (тот же адрес статьи) в пределах одного прохода получает источник выше в списке, обычно первоисточник, кто бы ни ответил быстрее. Статья, уже сохранённая раньше (например, первоисточник в тот час не ответил), остаётся у своего источника. Таймаут 10 секунд на ленту, один повтор при сетевой ошибке, предел 5 МБ, условные запросы по ETag. Источник с ошибками опрашивается реже: после второго сбоя подряд через 2 часа, потом 4, 8, 16, не реже раза в сутки; «Забрать сейчас» берёт все включённые сразу, но не держит экран: отвечает «Забор запущен», сам забор идёт после ответа, второй запуск во время первого не начинается. Итог виден в настройках после обновления страницы и в журнале.
- `MAIL_LOOP=off` выключает и цикл писем, и цикл новостей: забор лент, дайджесты новостей и очистку. Так работают сквозные тесты; «Забрать сейчас» в настройках работает и тогда.
- Защита забора от запросов во внутреннюю сеть: только http и https, только порты 80 и 443, без логина и пароля в адресе; имена без точки, localhost, `*.localhost`, `*.internal`, `*.local` запрещены. - Очистка раз в сутки: новости старше 180 дней, дайджесты старше 90, пустые еженедельные старше 15 (пустой еженедельный прошлой недели нужен, чтобы решить, догонять ли еженедельный), события «Мне» о дайджестах старше 90.

## Единая воронка, шаг 1: хаб и ОСАГО по СК (этап 58)

Ресурс читает второй источник, хаб «Единая воронка: данные». Это отдельная Google-таблица Арама, где боевые листы подтягиваются формулой IMPORTRANGE (вкладки с префиксом «src.»), рядом витрины. Боевые файлы и сам хаб ресурс не меняет, доступ служебному аккаунту только на чтение и только к хабу.

- Читаются два листа: «src.Все СК data_runrate» (полисы, премия и выручка ОСАГО по СК за месяц нарастающим итогом, пул и апсейл отдельно; обновляется день в день) и «План ОСАГО по СК» (модель «ОСАГО СК × каналы × регионы»: план месяца по СК). Колонки ищутся по заголовкам, лишние колонки и строка примечания над шапкой не мешают.
- Загрузка в два шага на странице прогноза, кнопка «Загрузить из хаба» у владельца и администраторов в режиме управления: «Проверить хаб» показывает, что прочитается, «Загрузить» пишет снимок «Все СК» на сегодняшний день по Москве и заменяет строки плана по СК. Повторная загрузка в тот же день заменяет снимок, журнал пишет действие `plan.hub`. Время загрузки факта и плана хранится отдельно (настройка `plan.hubPulled`: `fact` и `plan`, у каждой части время и кто загрузил; часть, которая не загрузилась, сохраняет прежнее время), карточка и панель пишут «Факт загружен ...» и «План загружен ...»: частичная загрузка не выдаёт себя за полную. Ссылку на хаб задаёт владелец в той же панели; боевые таблицы ресурса туда вставить нельзя: рабочий Bord, боевой LRF, таблица задач Bord (`bord.sourceId`), зеркало задач (`sheet.spreadsheetId`), источник LRF (`plan.sourceId`, по умолчанию таблица-связка) и источник цифр недели (`numbers.sourceId`).
- Загрузка из двух независимых частей: снимок факта («Все СК») и план по СК. У каждой части в проверке свой статус «загрузится» или «не загрузится» с причинами и предупреждениями. Сломанный лист плана не мешает снимку факта и наоборот: что прошло проверку, то загружается, журнал пишет, что загружено и почему другая часть нет. Обе части не готовы: загрузка отказывает с причинами обеих и ничего не пишет.
- Что блокирует часть (лучше не загрузить, чем молча записать неполное или пустое). План по СК: ошибка формулы (#REF!, #N/A, #VALUE!, #DIV/0! и т.п.) в полисах за текущий месяц у отобранной строки (с названием СК), ошибка в подписи строки, которая по остальным подписям проходит отбор (чья она, не понять), нет колонки текущего месяца, у полисов за текущий месяц нет ни одного числа у СК (число только в строке итога не в счёт), у всех СК полисов за месяц 0 при итоге больше нуля, повтор строки СК (с названием), повтор колонки периода, лист длиннее лимита строк. «Все СК»: строка с названием СК без месяца или без числа полисов (с названием СК), строка месяца снимка с ненулевыми полисами, но пустым PARTNER_NAME (с номером строки), ошибки формул в нужных ячейках, лист длиннее лимита строк (5 000), нет строк ни за текущий, ни за прошлый месяц (1-го числа: нет строк прошлого месяца), итог месяца упал против прошлого снимка того же месяца больше чем на 1% (лист мог обрезаться: снимок не пишется, чтобы не перетереть факт и закрытие месяца).
- Предупреждают, но не блокируют: остальные ошибки формул в плане (КВ за год, прошлые месяцы, подписи строк чужих каналов и регионов: такие ячейки пишутся пустыми, в предупреждении сколько ячеек и у каких СК), лист шире 60 колонок, нет колонки POOL, WITH_UPSALE или колонки выручки, сумма СК в плане не сходится с итогом, строки «Все СК» с одинаковым ключом сложены (счётчик повторов и пример), итог месяца не вырос с прошлого снимка, хотя день факта сдвинулся («источник, похоже, не обновился с прошлой загрузки»; закрытый месяц расти не обязан), СК из прошлого снимка нет сегодня, названия СК в двух листах не свелись (список несовпавших). Лист есть, но пустой: «лист пустой»; листа нет: «не найден в хабе».
- Названия СК сводятся по ключу `skKey` (`src/lib/plan/hub.ts`): без учёта регистра, пробелов, кавычек всех видов, ё/е, дефисов и тире, формы собственности и типовых слов в начале и в конце названия (АО, ПАО, ООО, САО, СПАО, ОСАО, СК, «Страховая компания», «Акционерное общество»). Слово «страхование» и всё остальное остаётся частью имени: «Сбербанк страхование» и «Сбербанк страхование жизни» разные СК. «Итого», «ИТОГО» и «Всего» считаются итогом. Разные написания одной СК («РГС» и «Росгосстрах») сводит справочник соответствий: настройка `plan.skAliases` вида `{ "<название в Все СК>": "<название в плане>" }`, владелец правит его в панели хаба текстовым полем «название = название» по строке, каждая правка в журнале `plan.skAliases`. Справочник применяется к обоим листам при показе (в снимках названия хранятся как в листе), поэтому правка действует и на уже загруженные снимки, а строка, записанная наоборот, тоже сводит СК. Строка карточки называется как в плане.
- В «Все СК» строки с одинаковым ключом (месяц, СК, пул, апсейл) складываются. Строка без месяца и без названия (например, сумма под таблицей) строкой СК не считается. В плане берутся строки раздела «Воронка» с каналом ровно «все каналы» и регионом ровно «все регионы». Объединённые ячейки (значение только в первой строке) протягиваются вниз по старшинству: СК, внутри СК Раздел, внутри Раздела Канал, внутри Канала Регион; смена СК сбрасывает Раздел, Канал и Регион, чтобы подпись чужой СК не протягивалась. Заголовки периодов датой (Google отдаёт их числом) читаются как месяц.
- Снимок хранит только текущий месяц по Москве и прошлый месяц (для закрытия), если он есть в листе: таблица снимков не растёт историей листа. 1-го числа снимок хранит только прошлый месяц (см. правило дня факта ниже), строки нового месяца в него не идут; если строк прошлого месяца нет, снимок не грузится.
- Факт в «Все СК» по вчерашний день (решение Арама 22.10): день с фактом = день загрузки по Москве минус один, по нему считаются прошедшие дни месяца для ранрейта. Снимок, сделанный 1-го числа, относится к закрытию прошлого месяца (итог прошлого месяца), дневной факт текущего месяца с него не считается. 1-го числа у текущего месяца факта ещё нет: ранрейт не считается, карточка пишет «Факт за месяц появится завтра». Снимок после конца месяца (закрытие и поздние поправки) относится к последнему дню месяца, подпись и счётчик дней прошлого месяца не выходят за его пределы. Правило в `src/lib/plan/hub.ts`: `FACT_LAG_DAYS`, `factDay`, `snapshotDayIn`.
- Выручка-факт ОСАГО по СК с апсейлом, как в плане (решение Арама 22.10): `POLICIES_REVENUE_WO_VAT` плюс `UPSALE_REVENUE_WO_VAT`. Колонки апсейла нет в листе: предупреждение в проверке, выручка без апсейла. Правило в `src/lib/plan/hub.ts`: `REVENUE_FACT_COLUMNS`.
- Дневной факт по СК получается из снимков: факт за день это разница со снимком предыдущего дня того же месяца. Поэтому хаб стоит загружать каждый день, лучше в одно время. Снимок, загруженный раньше вчерашнего дня, помечается в карточке. СК, которой нет в последнем снимке, но которая была в прошлом снимке того же месяца, идёт в итог по дням со своим прошлым значением (нарастающий итог не убывает от того, что СК пропала из листа), в превью об этом предупреждение, в строке СК пометка «Нет в последнем снимке: факт на ...». Если СК в листе переименовали, задайте соответствие названий, иначе старое название останется в итоге со своим прошлым значением.
- В карточке ОСАГО раздел «ОСАГО по СК: план, факт и ранрейт»: план месяца из модели, факт с начала месяца, доля пула, ранрейт до конца месяца и отклонение от плана, итог и сверка итога с LBE полисов из LRF (это разные версии, расхождение нормально). Ранрейт и «К плану» показываются, когда в месяце набирается 3 дня факта (при факте по вчерашний день это 4-е число, `HUB_LIMITS.minRunRateDays`); до этого колонок нет, карточка пишет «Ранрейт и отклонение от плана появятся с 4-го числа». Ранрейт линейный по дням; когда в месяце набирается 14 дней с дневным фактом (есть снимок за день и за предыдущий день; первый снимок месяца дневного факта не даёт), включается профиль дней недели (средний факт каждого дня недели, остаток месяца по календарю), при расхождении методов больше 10% показываются оба. Колонок выручки в «Все СК» нет: выручка по СК «нет», а не ноль.
- Выручка и КВ по СК видны управлению, команде ОСАГО и команде партнёрского канала, и только при личном входе или в режиме владельца: под общим логином можно выбрать чужой профиль, поэтому там этих колонок нет (то же правило, что у корректировки и выгрузки прогноза). Остальные видят полисы, план и ранрейт без этих колонок. Снимки лежат в `plan_sk_snapshots`, план по СК в `plan_sk_lines`.
- Доступ по уровням этапа 57: раздел по СК и действия хаба (проверка, загрузка, ссылка на хаб, соответствие названий) только у тех, кому открыты все цифры. Проверку уровня делают действия и сборка раздела `skView`, поэтому уровню «основные цифры» сводка месяца приходит без разреза по СК, а закрытому уровню не приходит ничего. Права управления на загрузку и права владельца на ссылку и справочник названий остаются как были.
- Раздел по СК собирается только там, где он нужен: `monthPlan(..., { sk: false })` не читает снимки и настройки хаба. Так собираются сводка для отчёта CEO, встречи и сводки (`planBrief`), выгрузка в Excel и ответы на корректировку и отметку «Прогноз проверен» (экран оставляет у себя прежний раздел по СК, `skOmitted`). Экран прогноза передаёт уже известный уровень доступа (`{ level }`), раздел не считает его заново; из снимков и строк плана выбираются только нужные поля.
- Без ключа Google (`SHEET_FAKE=1`) хаб имитируется четырьмя СК с выдуманными цифрами: так проверяют экран и тесты.

## Рынок КАСКО и ОСАГО (этап 62)

Решение Арама 22.10: рынок КАСКО и ОСАГО в материалах платформы, раздел доступен только отдельным людям, на встрече разбираем его в начале каждого месяца.

- Раздел «Рынок» (`/market`, группа «Бизнес» в меню): дашборд рынка с вкладками КАСКО и ОСАГО внутри. Вкладка и фильтры живут в адресе (`/market?tab=o-insurers&geo=top4`), ссылкой можно поделиться. Над дашбордом строка «Данные от <дата загрузки>, загрузил <имя>».
- Кто видит (этап 72, решения Арама 23.10): владельцы всегда (роль читается из базы на каждом запросе: новый владелец видит раздел сразу, снятая роль закрывает его, если человека нет в списке); любой, кто сейчас в режиме управления, в том числе администратор (администратор без режима только если он в списке); все, кто вошёл по общему логину, любым выбранным профилем; при личном входе без режима управления остальные по списку, который владелец ведёт в режиме управления: «Настройки», раздел «Рынок КАСКО и ОСАГО». Проверка на сервере у страницы, обработчика данных, кнопки «Открыть рынок» на встрече; пункт меню и командная строка берут то же правило. Загрузка пакета по-прежнему только владелец при личном входе. Пункт меню «Рынок» только тем, кому раздел открыт; остальным страница пишет «Раздел открыт отдельным людям, доступ даёт владелец», обработчик данных отвечает 403 без цифр. Правка списка пишется в журнал (`settings.marketAccess`), люди, которых больше нет или они выключены, считаются и показываются в настройке. События рынка в журнале (загрузка пакета, люди с доступом, команды разбора: записи об объекте `market` и настройки `market.*`) видят только те, кому раздел открыт при личном входе (`canSeeMarketEvents`): администратор без доступа к рынку их в журнале не видит, по общему логину их нет, режим управления сам по себе их не открывает (права журнала этап 72 не менял). Тот же фильтр у выгрузки в Excel (лист «Журнал»): по тому, кто выгружает.
- Настройка доступа (этап 72): Арам добавил шесть человек и не сохранил, потому что кнопка «Сохранить» была одна внизу под списком команд. Теперь под плашками людей, как только список отличается от сохранённого, строка «Не сохранено: добавить N, убрать M» с кнопками «Сохранить доступ» (сохраняет только людей) и «Отменить» (возвращает сохранённый список), кнопки 44 px. После сохранения уведомление «Доступ к рынку сохранён: раздел видят N человек» и новый счётчик «Сейчас раздел видят N человек, из них владельцев M, плюс администраторы в режиме управления и все, кто входит по общему логину» (про общий логин только пока он включён). Под командами разбора такая же строка с «Сохранить разбор»; нижняя «Сохранить» сохраняет оба списка. Обработчик сохраняет только переданные списки. Пока есть несохранённые правки, браузер переспрашивает при закрытии и перезагрузке (`beforeunload`), а щелчок по ссылке внутри приложения спрашивает подтверждение (`src/components/admin/use-leave-guard.ts`); переходы из командной строки не перехватываются.
- Данные и код дашборда хранятся только в базе (таблицы `market_bundles` и `market_datasets`), в репозитории их нет. Обновление: владелец при личном входе нажимает «Загрузить пакет рынка» на странице раздела и выбирает пакет. Пакет рынка это один файл JSON до 25 МБ: `{ "kind": "weekly-market-bundle", "version": 1, "files": { "index.html": ..., "ui.js": ..., "d3.min.js": ... }, "datasets": { "<имя>": { "title", "description", "rows": [...] } } }`. Файлы `index.html` и `d3.min.js` обязательны: дашборд вызывает d3 уже в первом скрипте, пакет без него не принимается. Новый пакет целиком заменяет прежний одной транзакцией, в журнал (`market.upload`) пишется только число наборов и строк. Блок «Обновить данные НСИС» внутри дашборда спрятан: данные обновляются загрузкой пакета.
- Собрать пакет из выгрузки дашборда-артефакта: `node scripts/market-bundle.mjs <папка выгрузки> --out <файл.json> [--d3 <путь к d3.min.js>]`. Папка: `datasets/*.json` (описание набора), `blobs/<id>.json` (строки), `files2/files/` или `files/` (код страницы). Библиотека d3 берётся из `node_modules/d3` (пакет `d3` в devDependencies) или из пути `--d3`. Путь `--out` внутри папки репозитория (и через ссылку на папку) скрипт не принимает: цифры рынка не должны попасть в git. Если `--out` уже существует как ссылка, тоже отказ: запись пошла бы туда, куда она ведёт. Вдобавок имена `market-bundle*.json` в `.gitignore`.
- Безопасность: дашборд работает в изолированном окне (`iframe sandbox="allow-scripts"` без `allow-same-origin`), у окна непрозрачный источник, cookies и API приложения ему недоступны. Внутри окна политика CSP закрывает сеть и внешние файлы, файлы пакета встраиваются в страницу окна. Данные страница берёт сама (`/api/market/data`, проверка доступа, `Cache-Control: no-store` без ETag и ответов 304, как у остальных API: цифры не ложатся в кэш браузера) и передаёт окну сообщением только в ответ на `ready` с одноразовой меткой окна, не чаще раза между событиями `load` и каждому документу окна один раз: событие `load` само данных не отправляет (иначе их получила бы страница, на которую окно ушло бы по ссылке), повторные `ready` 5 МБ не дублируют. Вместе с данными уходят текущие вкладка, фильтры и тема: после перезагрузки документа окна возвращаются они, а не вшитые в страницу окна. Окно никуда не уходит: щелчок по ссылке не на якорь (`#...`) гасится, `window.open` ничего не открывает. Готовый текст ответа (мегабайты) сервер держит в памяти процесса по версии пакета: на запрос из базы читаются только номер версии и время загрузки, совпали, отдаётся готовый текст; загрузка пакета память сбрасывает. Сообщения от окна принимаются только от него, только с одноразовой меткой этого окна (её родитель кладёт в `__MARKET_BOOT__` окна, окно возвращает её в каждом сообщении; метка отсекает чужие окна и страницы, а не код самого пакета: в тексте страницы окна она видна) и только по схеме: высота, вкладка, фильтры. Ответ не JSON экраны разбирают по статусу: 401 вход закончился, 413 файл больше 25 МБ, остальное общий текст. Среда, которую ждёт код дашборда (`window.dash`: расчёты, наборы, фильтры, вкладка, палитра), собрана в `src/lib/market/runtime.ts`, токены оформления двух тем в `src/lib/market/theme.ts`.
- Встреча: на первой встрече команды в календарном месяце (раньше в этом месяце встреч этой команды не было) первым пунктом встаёт «Рынок КАСКО и ОСАГО: итоги <прошлого месяца>». Решение: пункт появляется только когда пакет рынка загружен, без данных разбирать нечего. Команды выбирает владелец в том же разделе настроек (`settings.marketMeeting`), по умолчанию топ-команда. Пересборка повестки пункт не дублирует, убранный ведущим не возвращается. У пункта кнопка «Открыть рынок» (открывается в новой вкладке) только у тех, кому раздел открыт (с этапа 72 и в режиме управления, и по общему логину); остальные видят «Разбор рынка: открывают участники с доступом». Подпись пункта (день загрузки данных и предупреждение, если свежий пакет в этом месяце ещё не загружали) не хранится: её считает экран встречи при показе из текущих сведений о пакете, поэтому после загрузки свежего пакета она сразу новая. Подпись видят только те, кому раздел открыт (режим управления и общий логин с этапа 72 тоже; наблюдатели без доступа при личном входе нет), в протокол письма она не попадает.
- Загрузка пакета идёт мимо proxy: путь `/api/market/upload` исключён из `matcher` в `src/proxy.ts`, потому что для запросов с телом Next копит всё тело в памяти до вызова proxy и обработчика. Предел тела для proxy оставлен по умолчанию. Обработчик сам проверяет адрес страницы (Origin), вход (cookie сессии, профиль и устройство в базе; без входа ответ 401, а не перенаправление), права (владелец при личном входе) и размер по `Content-Length` до чтения тела, а тело читает потоком и обрывает на 25 МБ.
- Код: `src/lib/market` (проверка пакета `bundle.ts`, доступ и настройка `access.ts`, загрузка и выдача `service.ts`, пункт встречи `meeting.ts`, страница окна `srcdoc.ts`, адрес и сообщения `params.ts`), экраны `src/app/(app)/market` и `src/components/market`, обработчики `src/app/api/market`. Тесты на синтетическом пакете `tests/fixtures/market/bundle.json` (выдуманные цифры): `tests/unit/market.test.ts`, `tests/unit/market-routes.test.ts`, `tests/unit/market-answers.test.ts`, `tests/unit/market-access.test.ts` (этап 72: правило по общему логину, страница и обработчик данных, тексты «Не сохранено»), `tests/db/market.test.ts`, `tests/db/market-route.test.ts`, `tests/e2e/market.spec.ts`.

## Импорт наполнения (этап 67)

Задачи, решения, цели и связи задач с целями, собранные из истории проекта, загружаются одним файлом пакета (JSON, формат `weekly-napolnenie/1`, до 5 МБ; настоящий пакет меньше 1 МБ). Загружает владелец при личном входе в режиме управления: «Настройки», раздел «Импорт наполнения». Сначала ресурс показывает, что добавится, обновится и пропустится, каких людей и команд нет, что не загрузится и почему, что загрузится не так, как в пакете, что привяжется к ресурсу без изменений, и вероятные дубли. Загрузка идёт по кнопке «Загрузить».

- У каждой записи стабильный ключ: повторная загрузка того же пакета ничего не добавляет. Запись с тем же ключом и новым содержимым обновляется. В ключе у каждого поля хранится база: значение, которое загрузка оставила в ресурсе. Поле, которое после загрузки поменяли в ресурсе, загрузка не трогает ни в этот раз, ни в следующие, и предпросмотр заранее об этом пишет. Поле, которое загрузка не смогла записать (итог при том же статусе, пустое «Где сейчас», статус при поправленном итоге, срок закрытой задачи), остаётся с прежней базой.
- Рядом с базой в ключе лежит сама запись пакета. По ней предпросмотр видит, что пакет поменял поля, которые загрузка не меняет (у задачи ответственный, соисполнители, направление, команда, приоритет, источник, ссылки и дата закрытия; у цели владелец, команда и квартал; у решения дата и команда), и пишет «поправьте в ресурсе». Запись, в которой поменялось только такое или только то, что правили в ресурсе, считается пропущенной; у связи с целью новые уверенность или причина считаются «без изменений».
- Загрузка ничего не удаляет. Запись, которую удалили в ресурсе, загрузка не возвращает: «ключ есть, записи нет», запись пропускается. Удалённая или снятая цель не роняет загрузку: связь с ней и цель выше пропускаются с заметкой.
- «Перезаливка из выгрузки» удаляет задачи топ-команды и вместе с ними ключи этих задач и их связей с целями. Повторный импорт пакета ставит такие задачи заново (с новыми номерами), привязывает их к целям и возвращает связи решений с ними. Ключи решений и целей остаются: их перезаливка не удаляет.
- Задачи ставит служба задач от имени того, кто загружает: те же правила, номера, журнал, согласование. Номера новых задач берутся заранее короткой отдельной транзакцией, поэтому загрузка не держит настройку номеров, и задачи, которые люди ставят в это время, не ждут её. Лишние номера возвращаются, если после них никто номер не брал.
- Срок в прошлом бывает только у закрытой задачи из истории. Открытая задача со сроком в прошлом встаёт со сроком «Срок для задач без актуального срока»: одна дата на все такие задачи, по умолчанию через 14 дней после загрузки, владелец меняет её в предпросмотре (там же список этих задач). Тот же срок получает загруженная закрытая задача, которую пакет снова открывает, если её срок уже прошёл; она в том же списке. Исходным сроком у задачи остаётся срок из пакета, поэтому аналитика не считает её просроченной на неделе загрузки. Дата источника берётся из пакета, без неё пусто (задача со встречи без даты не попадает в повестку как поручение прошлой встречи). Закрытая задача из истории закрыта датой `closedAt` из пакета, без неё датой срока, если он прошёл, иначе датой источника: «закрыто на этой неделе» в аналитике от загрузки не растёт. Так же датируется закрытие, когда пакет закрывает уже загруженную или подхваченную задачу. О закрытых задачах из истории событий в «Мне» нет. «Узнают N человек» считает ответственных, соисполнителей и руководителей, которые согласуют задачи своих людей из других департаментов.
- Задачу, которую поставили в ресурсе до импорта, пакет подхватывает по номеру, названию и команде (`adopt: { "number": ..., "title": ... }`): новой задачи нет, ключ пакета привязывается к этой. Команда из пакета должна совпасть с командой задачи, а без команды в пакете ответственный из пакета должен быть в ресурсе и в команде задачи: задачу другой команды и задачу, команду которой сверить не с чем, загрузка не подхватывает (в списке «не загрузятся»). Названия сверяются после одной и той же чистки с обеих сторон. Другой ответственный в пакете виден в списке «загрузятся не так, как в пакете»: ответственного загрузка не меняет. Загрузка приводит к пакету статус задачи с итогом, «Где сейчас» и срок; название, «что нужно сделать» и ответственного ведут в ресурсе, и следующие загрузки их тоже не меняют. Закрытую задачу загрузка не открывает и итог её не меняет. Срок в прошлом из пакета не переносится, срок по умолчанию поверх своего подхваченная задача не получает, вероятным дублем она не считается. Кадровый фильтр для подхвата тот же. Под номером другая задача, задача в архиве или уже загружена с другим ключом: запись пропускается с причиной.
- Запись, которая уже есть в ресурсе (подхват без правок, цель с тем же номером без новых полей, задача уже с этой целью), не пропускается, а привязывается к ресурсу: загрузка запоминает её ключ и ничего в ней не меняет. Такие записи идут отдельным списком «Привяжется к ресурсу»; если поля цели в ресурсе отличаются от пакета, они перечислены («поля в ресурсе останутся: …»). При одних привязках кнопка «Загрузить» доступна.
- Цели заводит служба целей. Цель с тем же номером в той же команде (например, из борда лидера) не дублируется: у неё заполняются только пустые поля, и только они дальше принадлежат загрузке; остальные поля борда загрузка не перезаписывает. С пометкой `replace` цель приводится к пакету целиком (так цели ресурса выравниваются по бордам): тексты, целевые, владелец (от него зависит, чья это личная цель борда) и цель выше, если они есть в пакете; дальше вся цель принадлежит загрузке. Номер и источник цели не меняются; цели выше или владельца нет в пакете: в ресурсе остаются прежние, предпросмотр об этом пишет. Цель с `source: leader-board:<вкладка>` заводится как цель борда, то есть личная цель человека. Две цели пакета с одним номером в той же команде и квартале: вторая в списке «не загрузятся».
- Цель выше: в ключе цели хранится, какая цель выше стояла в ресурсе после загрузки и чья она. Загрузке принадлежит только цель выше, которую она сама поставила (или которая уже такая, как в пакете с `replace`). Цель выше, которую ставил борд или человек, без `replace` загрузка не меняет ни в первый раз, ни в следующие, пустую ставит; с `replace` приводит к пакету и во второй загрузке. Цель выше, которая в прошлый раз не встала (её цель не загрузилась), ставится, как только её цель загрузится, даже если запись цели ниже та же; пока не встала, предпросмотр об этом предупреждает. Свою цель выше, которую в ресурсе сняли или сменили после загрузки, загрузка не трогает. Решение, загруженное раньше, привязывается к задаче, которая получила ключ позже (поставлена заново или подхвачена со второго раза).
- Связь задачи с целью проверяется тем же правилом, что в карточке задачи, и по сроку, который будет у задачи после загрузки (срок переносится раньше, чем ставится связь). Цель, которую задаче поставили в ресурсе, загрузка не меняет, какая бы цель ни была в пакете, в том числе новая цель этого же пакета. Пакет перенёс связь на другую задачу: связь ставится новой задаче, у прежней цель остаётся. Две связи одной задачи в одном пакете (по ключу и по номеру это та же задача) противоречат друг другу: вторая в списке «не загрузятся». Решения без встречи пишутся в журнал решений команды с датой. Решение без команды не загружается («нет команды»): команду пишут в пакете.
- Не загружаются записи с кадровыми сведениями. Жёсткое правило: лучше не загрузить лишнее, чем загрузить кадровое; ложное срабатывание видно в предпросмотре и чинится переформулировкой в пакете. Кадровые всегда: зарплата, з/п и з/пл, ФОТ, фонд и оплата труда, оклады, грейды, декрет и отпуск по уходу, больничный человека, увольнение, «расстаёмся», уход из компании, испытательный срок, кандидат, вилка и сумма «на руки», гросс, компенсационный пакет, штатное расписание и штатные единицы, численность и хедкаунт, FTE, кадры, перформанс-ревью, премирование, премиальный фонд и бонусный пул, переменная часть, повышение до руководителя, аттестация людей. Кадровые связки по словам текста: премия или бонус рядом с людьми (сотрудники, менеджеры, МПП, лидеры, руководители, команда, отдел, КЦ) или с фамилией (по окончанию русской фамилии и по фамилиям людей ресурса из базы), оценка и калибровка людей и оценок, сокращение и оптимизация штата, позиций, должностей, вакансий, штатных ставок, людей. Страховой смысл снимает правило только у самой связки, а не у текста: сбор и объём премии, страховая премия, премия по продукту, полису, ОСАГО, премия страховщика, ставка КВ, комиссии, вознаграждения, тарифа, партнёрам и банкам, процентная ставка и «ставка 15%», калибровка оценок убытков, риска, скоринга, качества лидов, «по оценке аналитиков», лидеры рынка, специалисты Банка России, бонус компании, премия на конференции, выплата на больничном в продукте НС, человеко-часы, инвестиционный грейд, аттестация системы и агентов, зарплатный проект и банк. Проверяются все строки всех записей (ключи, номера целей в ссылках, источник цели, название подхвата, ссылки, причина связи), кроме ФИО и названий команд, и название пакета. Отсечённая запись подписывается без её текста: вид, номер по порядку в пакете и ключ, поле без кадрового слова; в пояснениях к другим записям она названа так же. Остальной пакет грузится; причина такой связи в ключ загрузки не попадает.
- Вероятные дубли того, что уже есть в ресурсе (задача: тот же ответственный, похожее название и срок не дальше 21 дня; решение: та же команда, та же дата и похожий текст), по умолчанию пропускаются. Разные числа в названиях (даты, годы, номера) значат разные записи, а не дубль. В предпросмотре у каждого дубля галочка «загрузить», галочка «Загрузить все дубли» включает все.
- Правила служб, которые иначе уронили бы загрузку, проверяет предпросмотр: подпись ссылки до 120 знаков и адрес до 500 (это ошибки пакета), скрытые направление и источник, наблюдатель ответственным, снятая цель, цель выше из другого квартала, не своей команды или с петлёй (цель грузится без неё; в петле без цели выше остаётся цель, которая идёт в пакете позже), задача, которая ждёт принятия.
- Всё одной транзакцией: ошибка правила, которую план не предвидел, откатывает всю загрузку. В журнале одна запись «content.import» с числами.
- Загрузка считает план без блокировок, потом внутри транзакции запирает только строки, которые запишет (задачи, которые правит или привязывает к цели, цели, у которых меняет поля или цель выше, решения, у которых меняет текст, владельца или статус; FOR UPDATE по порядку id), перечитывает их и считает план заново. Строки, на которые план только ссылается, и записи без изменений не запираются. Правка запертой строки во время загрузки ждёт её конца, но службы ресурса ждут не дольше 5 секунд: если загрузка дольше, правка не пройдёт, сотрудник увидит ошибку и повторит её после загрузки. То, что в ресурсе уже так, загрузка считает «без изменений». Если Postgres снимет загрузку из-за взаимной блокировки со встречной правкой, база остаётся как была, а владелец видит «Загрузку прервала одновременная правка в ресурсе, повторите загрузку». Поэтому загружайте в тихое время, когда в ресурсе мало правок: загрузка обычно идёт секунды (на настоящем пакете меньше 10 секунд); новые задачи людей загрузка не держит.
- Известное ограничение службы целей (не импорта): правка цели читает цель без блокировки до проверки цели выше, поэтому две одновременные правки целей выше в разных карточках могут составить петлю. Импорт её не создаёт: цели выше пакета проверяются на петлю в плане по ресурсу и пакету вместе.
- Обработчик `/api/content-import` идёт мимо proxy, как загрузка пакета рынка: он исключён из `matcher` в `src/proxy.ts`. До чтения тела обработчик сам проверяет адрес страницы (Origin), вход (без входа ответ 401 текстом, а не перенаправление), права и размер по `Content-Length`, а тело читает потоком и обрывает на 5 МБ. Странный JSON (списки вместо текста, глубокая вложенность) даёт список ошибок, а не сбой. Экран отправляет на загрузку тот же текст пакета, что был в предпросмотре. Тексты пакета чистятся так же, как текст разбора встречи: тире и стрелки становятся дефисом, точка посередине запятой, знаки нулевой ширины и мягкий перенос убираются.
- Пакет с внутренними именами и цифрами в репозиторий не кладётся. Пример формата с выдуманными данными: `tests/fixtures/content-import/package.json`.

## Смотреть как (этап 63)

Решение Арама 22.10: общий логин остаётся как есть (на экране выбора по-прежнему только топ-команда, остальные входят по личной ссылке), а владелец может посмотреть приложение глазами любого человека компании.

- Кто включает: только владелец (в том числе совладелец) при личном входе и в режиме управления владельца. Общий логин, администраторы и остальные пункта не видят, сервер им отказывает. Пункт «Смотреть как…» в меню профиля и команда в командной строке (Ctrl+K). Окно выбора ищет по ФИО, должности и подразделению среди всех включённых людей компании, список прокручивается, на телефоне окно во весь экран. Выключенного человека и себя выбрать нельзя.
- Что видно: всё так, как видит выбранный человек при личном входе: «Моя неделя», «Мне», задачи, команды, профиль, доступ к цифрам прогноза и к рынку по его правам. Режим управления на время просмотра выключен; в сессии владельца он остаётся и после выхода из просмотра снова действует, если срок не вышел. Встречи один на один в просмотре закрыты: их видят только двое участников, роль владельца их не открывает (правило этапа 28); их события не попадают в «Мне», на главную и в счётчик меню. Анонимная оценка встреч тоже закрыта, и напоминания о ней на главной нет: по нему видно, ответил ли человек. Вверху каждой страницы плашка «Вы смотрите как <ФИО>. Изменения недоступны» со временем окончания и кнопкой «Выйти из просмотра», та же кнопка в меню профиля и в командной строке. Плашка прилипает под шапкой на всех экранах (липкая строка столбцов Roadmap встаёт под ней), на телефоне в ней короткая строка «Как <имя>, до ЧЧ:ММ», а в шапке у аватарки значок просмотра. В названии вкладки браузера пометка «Как <ФИО>». Команда, выбранная в просмотре, живёт в своей cookie и уходит вместе с просмотром: выбор команды владельца не меняется.
- Только просмотр. Проверка записи одна: `assertWritable` в `src/lib/auth.ts`. Через неё идут `runAction` и `writingActor` (`src/lib/action-runner.ts`), которыми пользуются серверные действия экранов, `requireWriteContext` для действий, которые сами читают вход (задачи, weekly, сохранённые виды, режим управления), обработчики с изменениями (цели из борда лидера, пакет рынка) и выгрузка прогноза в Excel (она пишет журнал от имени выгружающего). Отказ одним текстом «В режиме «Смотреть как» изменения недоступны», ошибкой правила: экраны показывают его как есть. Действия, которые только читают (карточка задачи, история, связи, поиск, неделя для встречи, цели для выбора, прогноз лидера, просьбы по задаче, переключатель команды), идут через `runRead` или `requireContext` и в просмотре работают. События «Мне» не отмечаются прочитанными и разобранными (это тоже действия), письма и уведомления не уходят, черновики weekly с устройства и подписка браузера на уведомления в просмотре не сверяются. Черновики weekly выбранного человека на устройство владельца не пишутся, автосохранения в просмотре нет. Выход из ресурса всегда сначала снимает просмотр, если он был, потом отправляет с устройства черновики самого владельца и стирает черновики; если сервер отказал из-за просмотра, черновики остаются на устройстве.
- Безопасность: состояние просмотра в отдельной подписанной cookie `wk_view_as`. Ключ выводится из ключа сессий отдельно и у подписи своя метка назначения, поэтому cookie сессии и cookie просмотра не подменяют друг друга. В cookie номер просмотра, владелец, запись его устройства, выбранный человек, срок просмотра (2 часа, но не дольше режима управления) и срок режима управления. Вход проверяет её на каждом запросе: та же запись устройства и тот же профиль, владелец всё ещё владелец при личном входе в том же режиме управления владельца (включённый заново режим это уже другой режим), выбранный человек включён, срок не вышел. cookie другой сессии (прежний вход в этом браузере) не в счёт.
- Конец просмотра в старой вкладке (правки двух кругов проверки). Метка вкладки: страница (ViewAsSync) один раз оборачивает `window.fetch` (через него Next отправляет серверные действия и экраны загрузки) и добавляет к запросам с заголовком Next-Action и к изменениям через /api заголовок `X-Weekly-View` с состоянием, в котором сервер показал вкладку: `view:<номер просмотра>`, `ended:<номер>` или `self`. По метке `requireWriteContext` решает: вкладка просмотра пишет, только пока идёт тот же просмотр (и то с отказом «изменения недоступны»), а если просмотра с этим номером нет (вышли кнопкой в другой вкладке, срок, новый просмотр), отказ «Просмотр закончился, обновите страницу»; вкладка закончившегося просмотра (`ended`) тоже получает этот отказ; обычная вкладка владельца (`self`) во время просмотра получает отказ «изменения недоступны», а после конца просмотра пишет как обычно; запрос без метки (страница без скрипта, прямые запросы) по прежнему правилу: во время просмотра отказ, после конца, пока cookie на месте, «просмотр закончился». Правило в `viewAsWriteRefusal` (`src/lib/view-as.ts`), метка в `src/lib/view-as-fetch.ts`. Сама cookie живёт до конца режима управления и ещё 12 часов, а не до конца просмотра. Если просмотр закончился сам (срок, режим управления, роль, человека выключили), страницы показывают владельца с плашкой «Просмотр как <ФИО> закончился: <причина>» и кнопкой «Вернуться к себе» (возвращает на ту же страницу). Снимают cookie только «Выйти из просмотра» и «Вернуться к себе», выход из ресурса, новый вход в этом браузере, новый просмотр, а также включение и выключение режима управления после конца просмотра: эти действия во время просмотра отказывают ответом, а после его конца разрешены из любой вкладки, чтобы владелец не застрял. Записанный конец окончателен: если причина ушла (роль вернули, человека включили), просмотр не продолжается. В браузере плашка перезагружает вкладку в срок просмотра по остатку времени с сервера, а не по часам устройства (и при возврате на вкладку, если срок вышел, пока она спала); если после перезагрузки просмотр ещё идёт, следующая попытка не раньше чем через 30 секунд. Каждая вкладка при открытии и при возврате из кэша браузера объявляет остальным своё состояние через BroadcastChannel (запасной путь событие storage): вкладка просмотра или закончившегося просмотра с другим состоянием перезагружается сама, а обычную вкладку владельца закрывает плашка «В другой вкладке начат просмотр» с кнопкой «Обновить», чтобы не потерять набранный текст.
- Журнал (тип «Входы»): «viewAs.start» (кого и до какого времени) и «viewAs.stop» (кого и почему кончилось: «Выйти из просмотра», «Выход из ресурса», «Вышел срок просмотра», «Закончился режим управления», «Снята роль владельца», «Человек выключен», «Вход завершён»), от имени владельца. Если просмотр закончился сам, конец пишет первый запрос, который это увидел, а если такого не было, «Вернуться к себе», выход из ресурса, новый вход или новый просмотр. Начало и конец связаны номером просмотра (поле «было»; экран журнала и выгрузка в Excel его не показывают), конец одного просмотра пишется один раз. Записи о просмотре видят все, кому открыт журнал: владельцы и администраторы в режиме управления. Это сделано намеренно: администратор видит, что владелец смотрел глазами коллеги.
- Код: правила и cookie `src/lib/view-as.ts`, выбор, начало и конец `src/lib/view-as-service.ts` и `src/app/actions/view-as.ts`, окно выбора, плашки и метка вкладки `src/components/shell/view-as.tsx` и `src/lib/view-as-fetch.ts`. Тесты: `tests/unit/view-as.test.ts` (подпись, срок, привязка к сессии, правила, метка вкладки; по тексту кода обработчики с изменениями идут через проверку записи, вход для чтения только у перечисленных функций), `tests/db/view-as.test.ts` (кто может, когда гаснет, журнал, метка вкладки, режим управления после конца; каждое серверное действие ресурса в просмотре отказывает без метки и с меткой обычной вкладки, база не меняется, письма не уходят, чтение работает), `tests/e2e/view-as.spec.ts`.
- Новое серверное действие, которое что-то меняет, пишется через `runAction` (вторым аргументом приходит весь контекст входа, например запись устройства) или `requireWriteContext`. Если оно только читает (`runRead`, `requireContext`, помощник `reader()`), его имя добавляют в список чтения в `tests/unit/view-as.test.ts` (проверка по функциям) и в `tests/db/view-as.test.ts`: по умолчанию тесты требуют, чтобы любое действие в просмотре отказало.

## Weekly по смысловым блокам (этап 66)

Решение Арама 22.10: из weekly для CEO должно быть понятно, о каком продукте речь. Weekly делится на смысловые блоки, каждая строка подписана продуктом, у цифр ссылка на источник. Топ-команда называется «Команда страхования и инвестиций». Такие же блоки каждый руководитель может задать weekly своей команды.

- Стандартный набор блоков отчёта CEO, по порядку: «Новости рынка и команды», «Неделя к неделе», «Месяц: к прошлому году, к прошлому месяцу, план продаж», «Конкуренты», «Продукты» (подраздел на каждый продукт из справочника направлений, кроме партнёрки), «Партнёрский канал», «Риски», «План на неделю». После блоков, как раньше, живые «Решения недели», «Благодарности» и «Мои встречи недели», если заполнены.
- Строка блока: продукт (код направления из справочника), текст, ссылка на источник и её подпись. Продукт у строки есть всегда: строка без своего продукта подписывается «Департамент».
- Автосборка (`src/lib/weekly-blocks/assemble.ts`, чистые функции; данные из базы `sources.ts`):
  - новости рынка: новости модуля новостей с датой публикации в неделе отчёта (понедельник-воскресенье по Москве), не больше двух на продукт и шести всего, ссылка на статью; новости конкурентов сюда не попадают;
  - новости команды: записи weekly с блоком «Команда и процессы»;
  - неделя к неделе: цифры недели из недельного отчёта, рост или падение в абсолютных и процентах (доли в процентных пунктах), ссылка на «Прогноз», вкладка «Цифры недели»; продажи по дням, если обе недели загружены целиком. Нет отчёта, цифр или недели в отчёте: честное «Нет данных: ...»;
  - месяц: прогноз месяца недели (LBE с корректировками) против бюджета по продуктам (продажи и выручка, «план выполняем» или «не выполняем» с процентом) и итог по выручке; прошлый месяц и тот же месяц прошлого года берутся из LRF, только если эти месяцы в ресурс загружены, иначе строка «Продажи и выручка к прошлому году (...): нет данных, в LRF этого месяца нет». Подпись сравнения говорит, что сравнивается: «продажи к прошлому году» у продукта, «выручка к прошлому году» в итоге, «ранрейт к прошлому месяцу» у хаба; ОСАГО по СК из хаба (факт с начала месяца, ранрейт к плану, к прошлому месяцу) только для текущего среза и только у кого все цифры; ссылка на «Прогноз» месяца;
  - конкуренты: новости недели, в заголовке или описании которых есть слово конкурента. Имя самой ленты признаком не считается: новости ленты Банки.ру не становятся новостями о Банки.ру. Нет таких новостей: блок скрыт и появится сам, когда они будут;
  - продукты и партнёрский канал: записи weekly команды с отметкой «В отчёт CEO» (как раньше); если отметок за неделю нет, все записи weekly команды, экран это пишет. Запись идёт по своему направлению, риск в «Риски», план в «План на неделю», «что делаем дальше» строкой в план; ссылка на первый артефакт записи. Плюс черновик последнего готового разбора встречи команды за неделю и задачи команды, закрытые на неделе (не больше трёх на продукт, важные первыми);
  - риски: записи с риском, открытые задачи под риском и заблокированные (с пояснением), цели квартала в риске;
  - план на неделю: задачи со сроком на следующей неделе (не больше трёх на продукт) и записи «План» и «что делаем дальше».
- Редактор на странице «Отчёт CEO»: строку можно поправить, сменить продукт, убрать ссылку или строку, добавить строку; блок можно поднять, опустить, скрыть (в отчёт не попадёт) и собрать заново из источников. «Собрать заново» пересобирает все блоки, «Мои встречи» остаются. «Что получит CEO» показывает собранный отчёт без скрытых и пустых блоков. Сравнение с прошлой неделей показывает строки прошлого отчёта под каждым блоком. Копия текста и письмо: видимые блоки по порядку, потом обещания, решения, благодарности и встречи.
- «Отправить CEO» на странице «Отчёт CEO» (и, как раньше, из разбора встречи): только в приложении, владелец или администратор в режиме управления при личном входе. Отчёт сохраняется и помечается отправленным со снимком блоков, CEO получает событие в «Мне» и видит отчёт по блокам только для чтения. Правка после отправки: CEO видит отправленную версию и пометку.
- Хранение: поле `ceo_reports.blocks` рядом с прежними разделами. При сохранении блоков главное, риски и что дальше собираются из них (их читают выгрузка в Excel и старые экраны), снимок отправки хранит и блоки. Старые отчёты (только разделы) CEO видит как раньше; в редакторе такой отчёт разложен по блокам с живыми цифрами и переходит в блоки после сохранения. Сохранение разделами (старая вкладка) снимает блоки. Миграция данных не нужна.
- Конкуренты: список с ключевыми словами ведёт владелец на странице «Отчёт CEO», свёрнутый блок «Конкуренты» (настройка `ceo.competitors`, правка в журнале `ceo.competitors`), администраторы видят список. Слова ищутся как ключевые слова новостей: по началу слова, в кавычках целиком. Ещё два вида слов: «Т-Банк + агрегатор» (оба слова в одной фразе) и минус-слово «-Т-Страхован» (такое слово в новости не считается). Т-Банк в стартовом списке это агрегатор и сервис сравнения страховок, а не банк и не страховщик «Т-Страхование».
- Разбор встречи из Notion: Claude отвечает черновиком по блокам (новости, конкуренты, продукты, партнёрка, риски, план) с кодом продукта у каждой строки; прежний вид ответа (разделы строками) принимается и раскладывается по блокам. Разбор правилами понимает разделы «Новости», «Рынок», «Команда», «Конкуренты», «Партнёры», «Продукты» и разделы с названием продукта («ОСАГО», «Депозиты и инвестиции»); без них черновик собирается из итогов, решений, рисков и следующих шагов по продукту строки. Цифры недели и месяца из заметки не берутся. При отправке черновик дописывается к отчёту недели по блокам или заменяет свои блоки (выбор ведущего, если отчёт уже есть); отчёта нет: черновик дописывается к свежей автосборке, и CEO получает отчёт целиком.
- Weekly команды по блокам: руководитель команды (при личном входе), руководитель выше или режим управления задаёт блоки на странице `/weekly/team-report` (в ленте weekly кнопка «Отчёт по блокам»): из стандартного набора и свои, порядок. Шаблон хранится в `team_weekly_templates`, правка в журнале `team.weekly.template`, пустой список убирает шаблон. Участники видят на странице сдачи, что команда сдаёт weekly по блокам, и выбирают у записи «Блок отчёта» (`weekly_entries.section`; блок справочника и тип идут за ним). Руководитель видит отчёт команды, собранный по шаблону из weekly её людей, задач и целей команды, цифр и новостей по продуктам её людей, правит его, сохраняет (`team_weekly_reports`, журнал `team.weekly.report`) и отправляет своему руководителю: событие в «Мне» со ссылкой на отчёт, журнал `team.weekly.send`. Получатель видит отправленную версию только для чтения. Без шаблона weekly команды как раньше. Шаблон отдельным компонентом `src/components/weekly-blocks/team-template.tsx` и сервисом `src/lib/weekly-blocks/team.ts`: его можно встроить в карточку команды.
- Переименование: повторяемая миграция `20261022160620_top_team_name` меняет имя команды `top` на «Команда страхования и инвестиций», только пока у неё прежнее имя «Топ-команда»; имя, заданное руками, не трогается. Тексты интерфейса и сообщения сервера берут имя команды из базы (`topTeamName`, на экранах `teamName(TOP_TEAM)`), загрузка целей узнаёт команду и по прежнему имени. Внутреннее понятие `TOP_TEAM` в коде то же.
- Миграции: `20261022160600_weekly_blocks` (блоки отчёта CEO, блок записи), `20261022160610_team_weekly_blocks` (шаблоны и отчёты команд), `20261022160620_top_team_name`.
- Код: `src/lib/weekly-blocks` (модель и проверка блоков `types.ts`, правки редактора `edit.ts`, сборка `assemble.ts`, данные из базы `sources.ts`, конкуренты `competitors.ts` и `service.ts`, команды `team.ts`, шаблон автора записи `author.ts`), `src/lib/ceo/report.ts` (сохранение и отправка по блокам, отчёт глазами CEO), экраны `src/components/weekly-blocks`, `src/components/ceo`, `src/app/(app)/weekly/team-report`, действия `src/app/(app)/weekly/blocks-actions.ts`. Тесты: `tests/unit/weekly-blocks.test.ts`, `tests/unit/notion-parse.test.ts`, `tests/db/ceo-blocks.test.ts`, `tests/db/team-blocks.test.ts`, `tests/db/notion-meeting.test.ts`, `tests/e2e/ceo-blocks.spec.ts`.

### Правки по проверке (этап 66)

- Цифры по уровню доступа этапа 57. Строки с цифрами помечены (`figures`): блоки «Неделя к неделе» и «Месяц» целиком, строки со ссылкой на «Прогноз» и цифры недели (основные цифры), хаб ОСАГО по СК и выручка партнёрского канала (все цифры). Метка ставится при сборке и при каждой чистке блоков, поэтому строка, написанная руками в блоке цифр, тоже считается строкой с цифрами. При чтении (отчёт команды, его снимок, отчёт глазами CEO и других получателей, в том числе запасного профиля ceo) строки режутся по уровню зрителя на сервере: без доступа вместо них одна строка «Цифры видны только с доступом к цифрам», с основными цифрами без хаба и без разреза по партнёрам. Тот, кто видит не все цифры, правит отчёт как обычно: цифры, которых ему не показали, при сохранении возвращаются в свои блоки из прежней версии.
- Отчёт команды вне страхования не получает чужие продукты и итог выручки департамента: продукты команды это продуктовые направления её людей, «Департамент» (его получают все люди из загрузки структуры) продуктом не считается. Нет ни одного продукта: в блоках цифр честное «Цифр по продуктам команды нет: у людей команды не задано направление продукта».
- Живые цифры: «Неделя к неделе» и «Месяц» без правок руками пересобираются при показе и при отправке (CEO, руководителю, из разбора встречи), в снимок уходят свежие цифры. Правка строк блока помечает его поправленным (`edited`), такой блок сам не обновляется; если автосборка с тех пор изменилась (отпечаток `basis`), редактор пишет «Цифры обновились, пересобрать?». «Собрать блок заново» снова делает цифры живыми.
- Получатель отчёта команды (руководитель команды выше, иначе руководитель по структуре) видит отчёт только при личном входе и только отправленную версию: автосборка для него не считается. Команда выше выключена, без руководителя или её руководитель выключен: отчёт уходит руководителю по структуре. Себе отчёт не уходит.
- Задачи и цели в отчёте команды: самой команды и её людей без внешних участников, но не задачи и цели топ-команды (они уходят в отчёт CEO).
- Шаблон поменяли: сохранённый отчёт команды выравнивается по нему при показе, новые блоки встают на место из автосборки или пустыми, убранные уходят вниз скрытыми со своими строками.
- Блок записи weekly сверяется с шаблоном, по которому автор сдаёт weekly: чужой блок и блоки цифр не сохраняются, такие записи раскладываются по смыслу.
- «Заменить блоки» из разбора встречи: пустой блок черновика ничего не заменяет, собранные строки со ссылкой на источник (новости, задачи, артефакты) остаются, заменяются написанные.
- Разбор правилами: слова разделов «Рынок», «Команда», «Партнёры», «Конкуренты», «Продукты» считаются заголовком только с двоеточием, разметкой заголовка («## Рынок», «**Рынок**») или одним названием без слов после. «Рынок растёт», «Команда укомплектована», «Партнёры подписали договор» остаются фразами.
- «Вклад» и «инвестиции» подписывают строку депозитами только в продуктовом смысле («по вкладам», «вкладчик», «инвестиционный счёт»), «вклад команды» и «инвестиции в маркетинг» нет.
- Автосборка за один запрос страницы считается один раз (кэш на запрос), в разных запросах заново.

### Правки второго круга проверки (этап 66)

- Отчёт команды собирается со всеми цифрами, зрителю строки режутся по его уровню. Пометка «цифры обновились» считается по полной сборке, наружу уходит только признак. Блок цифр, хотя бы одна строка которого зрителю закрыта (у руководителя без доступа «Неделя к неделе» и «Месяц», у руководителя с основными цифрами «Месяц» со строкой хаба), для него только для чтения: без «Пересобрать», «Добавить строку» и правки строк. Сервер при сохранении берёт такой блок из прежней версии целиком (строки, пометка «поправлено руками», отпечаток), от зрителя остаются только место блока и «скрыт».
- Скрытый блок не уходит ни в снимок отправки (отчёт команды и отчёт CEO), ни в данные страницы получателя.
- Получатель отчёта команды по ссылке из «Мне» видит отправленную версию с отметкой «поправили после отправки», даже если сам может править (руководитель команды выше); рядом переход к текущей версии команды. Получатель считается для команды, а не для того, кто нажал: отправить отчёт самому себе нельзя, у получателя кнопки отправки нет.
- «Конкуренты» тоже живой блок: без правок руками пересобирается при показе и при отправке и появляется сам, когда появилась новость; поправленный руками помечается «появились новые новости конкурентов, пересобрать?».
- Т-Банк как витрина страховок: «Т-Банк + витрин», «Тинькофф + витрин». В словах конкурентов неразрывный дефис, короткое и длинное тире считаются обычным дефисом: «Т‑Банк» это «Т-Банк».
- Страница отчёта команды не обновляется сама на каждую правку weekly (каждый показ пересобирает отчёт): свежие источники по кнопке «Обновить источники». Команды, уровень цифр и справочник продуктов читаются один раз на запрос.
- Предпросмотр «Что получит CEO» в разборе встречи с живыми блоками, как уйдёт при отправке.
- Редактор блоков команды доступен и на неделе, где отчёт уже отправлен.
- Перезаливка из Bord не удаляет недели с отчётами команд и отправленными отчётами CEO; черновики отчёта CEO по-прежнему уходят.
- Подсказка в строке отчёта команды обращена к руководителю, в предпросмотре у руководителя без доступа к цифрам вместо закрытых цифр пометка, что их увидит получатель с доступом.
- Устаревшая вкладка (нет момента прошлого сохранения) проверяется внутри runAction: сначала его проверки, потом «Страница устарела».

### Решения Арама 22.10 (этап 66)

Подтверждено: стартовый список конкурентов; отчёт команды уходит руководителю команды выше, иначе административному руководителю; отчёт команды видят руководитель команды, руководители выше, режим управления и получатель, участники нет.

### На подтверждение Араму (этап 66)

- Ключевые слова Т-Банка в стартовом списке уточнены по проверке: «Т-Банк + агрегатор», «Т-Банк + сравнен», «Т-Банк + маркетплейс», «Т-Банк + витрин», «Тинькофф + агрегатор», «Тинькофф + сравнен», «Тинькофф + витрин», минус-слова «-Т-Страхован», «-Тинькофф Страхован». Ограничение прежнее: в ресурсе только новости, которые привязались к продуктам по их словам; новость о конкуренте без слов продуктов в блок не попадёт.
- Отметок «В отчёт CEO» за неделю нет: в блоки берутся все записи weekly команды страхования и инвестиций (иначе черновик пустой). Есть отметки: только отмеченные, как раньше.
- «Решения недели» и «Благодарности» остались живыми частями после блоков, а не строками блока «Новости рынка и команды».
- «К прошлому месяцу» по LRF это прогноз прошлого месяца (LBE с корректировками на конец месяца) как лучшее приближение факта; «к прошлому году» появится, когда в ресурс загрузят тот же месяц прошлого года.
- У команды страхования и инвестиций шаблона блоков нет: её отчёт это отчёт CEO со стандартным набором. Человек в нескольких командах сдаёт запись по шаблону первой команды, которая ждёт его weekly; блок чужого шаблона отчёт другой команды раскладывает по смыслу.

## «Мне» (этап 11, часть 1)

Раздел «Мне» в меню собирает, чего ждут от человека. События пишутся в той же транзакции, что и правка задачи:

- новая задача для вас или предложение задачи (его подтвердит владелец или администратор);
- задача передана вам, вы добавлены соисполнителем;
- комментарий к задаче, где вы ответственный, соисполнитель или автор;
- срок вашей задачи перенёс кто-то другой;
- ваше предложение или задача подтверждены.

Сам себе человек событий не получает, выключенный тоже. События одной задачи склеены в одну строку. «Разобрано» убирает строку, новое событие по задаче возвращает её. «Напомнить» прячет строку до 9:00 завтра или понедельника. Ниже событий сроки ваших задач: просрочено, сегодня, завтра. Число рядом с «Мне» обновляется при переходе и раз в 30 секунд.

Ещё не сделано (часть 2 этапа 11): упоминания @имя, комментарии и реакции к записям weekly, подписка на задачу, письма по непрочитанным событиям и напоминания о сдаче (нужны почтовый сервер и фоновый процесс), мгновенное обновление без ожидания 30 секунд.

## Оформление: токены (этап 10)

Цвета, размеры шрифта, тени, ширина страницы и анимации заданы один раз в `src/app/globals.css` (блок `@theme`). Экраны берут их классами: `text-caption`, `text-body`, `text-page-lg`, `bg-amber`, `shadow-menu` и так далее. Новый дизайн (этап 21) меняет значения там, экраны не трогаются.

- Шкала размеров по ролям: от `text-micro` (11) до `text-display` (44). Класс задаёт только размер, межстрочный интервал наследуется. Список с подсказками, где какой, на странице «Образец компонентов» (`/ui`).
- Имена токенов перечислены в `src/lib/design-tokens.ts`: по нему склейка классов `cn` понимает, что `text-caption` это размер, а не цвет.
- Тест `tests/unit/tokens.test.ts` не даёт вернуть зашитые значения: `text-[15px]`, цвет числом в классе или в коде, `shadow-[...]`.
- Проверка «вид не изменился»: `npm run test:visual -- --update-snapshots` снимает эталон всех экранов (ноутбук и телефон) на текущем коде, `npm run test:visual` после правок сравнивает по пикселям. Время и счётчики, которые меняются от прогона к прогону, перед снимком заменяются одинаковыми значениями. Эталоны в репозиторий не попадают.

## Правила безопасности

- 5 неверных паролей с одного адреса закрывают вход на 15 минут. То же для паролей режима управления.
- Режим управления открывает только пароль своей роли и действует 12 часов.
- Журнал изменений только дописывается: правку и удаление запрещает триггер в самой базе.
- Страницы закрыты от поисковиков заголовком и robots.txt.
- Пароли и `.env` никогда не попадают в чат, документы и репозиторий.
